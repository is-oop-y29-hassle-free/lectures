# Бриф для Claude Design: презентация «Лекция 6. Структурные паттерны»

## Общие требования

- **Формат:** 16:9, 144 слайда, язык — русский. Лекция для студентов 2 курса дисциплины «ООП и проектирование», читается за два занятия; точка остановки после блока 4 (слайд 82). Позади лекции по основам ООП, SOLID, GRASP, проектированию и порождающим паттернам; впереди ЛР2 — структурные паттерны. Основной референс студентов — книга А. Швеца «Погружение в паттерны проектирования».
- **Только светлая тема.** Аудитория светлая, проекторы старые, картинку просвечивает солнце.
  - Фон белый или почти белый, без серых заливок на весь слайд; текст почти чёрный.
  - Никаких тёмных слайдов, включая титул, разделители и блоки кода.
  - Тонкий светло-серый текст запрещён: минимальный контраст — как у тёмно-серого на белом.
  - Кегль основного текста не меньше 20 pt, сносок и источников — не меньше 16 pt, кода — не меньше 16 pt.
- **Цвета.** Палитра та же, что в лекции 5.
  - **Акцентный** — насыщенный тёмно-синий или тёмно-зелёный: определения, «правильный» код, позиция курса.
  - **Предупреждающий** — тёмно-красный: антипримеры, «так не делаем», заблокированный вызов.
  - Оба тёмные и плотные, не пастельные. Нейтральные серые — только для рамок и фона кода.
- **F-pattern на каждом слайде.** Взгляд идёт: заголовок → первая строка под ним → вниз по левому краю. Поэтому:
  - Заголовок — один тезис, а не название темы («Декоратор никогда не блокирует вызов», а не «Декоратор. Свойства»).
  - Под заголовком — **одна ключевая строка**: самое важное, что нужно унести с этого слайда.
  - Дальше — короткая колонка слева: не больше трёх пунктов, каждый в одну строку.
  - Всё крупное (код, схема, таблица) — справа от колонки или под ключевой строкой; не больше одного крупного объекта на слайд.
  - Никаких абзацев. Не помещается — значит, это два слайда. Сокращать содержание не нужно: лучше больше слайдов, чем плотнее.
- **Шесть шаблонов слайдов, использовать только их** (те же, что в лекции 5):
  - **A — Определение.** Заголовок; под ним акцентная плашка: рамка в акцентном цвете, слева вертикальная полоса, кегль крупнее основного.
    - Текст **дословный, менять нельзя**, включая пунктуацию.
    - Под плашкой мелким текстом — строка источника. Два вида источника, визуально различимые:
      - **из книги** — маленькая иконка книги + «А. Швец, «Погружение в паттерны проектирования», с. N»;
      - **формулировка курса** — без иконки книги, подпись «формулировка курса».
    - Помечены ниже как **[ОПРЕДЕЛЕНИЕ · книга, с. N]** или **[ОПРЕДЕЛЕНИЕ · курс]**.
    - На слайде только плашки, источник и, если указано, одна строка или мини-схема. Две-три плашки — одинаковой ширины, одна под другой; четыре — сеткой 2 × 2.
  - **B — Код.** Заголовок; ключевая строка; блок кода занимает левые ~60% ширины: светло-серый фон, тёмный моноширинный текст, подсветка синтаксиса насыщенными цветами, без нумерации строк. Справа — узкая колонка: до трёх пунктов «на что смотреть».
    - Внизу справа — сноска **«Для C++-человека»**, если указана: курсив, иконка стрелки C++ → C#.
    - Код приводится **дословно**: не переформатировать, не сокращать, многоточия `...` и `{ ... }` — часть кода.
    - Строки для подсветки указаны: фоном акцентного цвета — «смотреть сюда», предупреждающего — «так не делаем».
    - Слайд с антипримером — тонкая предупреждающая рамка по краю.
    - Если класс разрезан на два слайда, второй начинается с пометки «продолжение» мелким текстом над кодом.
  - **C — Тезисы.** Заголовок; ключевая строка; до трёх пунктов слева; справа — пиктограмма, мини-схема или пусто.
  - **D — Схема / таблица.** Заголовок; ключевая строка; схема или таблица по центру или справа; слева — не больше двух подписей. Таблицы — не больше 6 строк.
  - **E — Дискуссия.** Крупный вопрос (кегль как у заголовка), слева иконка двух реплик, внизу мелко — подсказка. Ответа на слайде нет.
  - **F — Книга и курс.** Две равные колонки: слева «Книга Швеца» — нейтральная рамка, иконка книги, номер страницы; справа «Курс» — акцентная рамка. Внизу на всю ширину — строка «Правило для ЛР2» акцентным цветом. Колонку книги **не** окрашивать предупреждающим цветом: это не ошибка книги, а другое решение. Если в колонке книги есть цитата — она дословная, в кавычках-ёлочках.
- **Сквозная схема «Обёртка и вызов».** Главный визуальный объект лекции: по нему студенты различают похожие паттерны. Базовый вид:
  - внешний прямоугольник с подписью «обёртка», внутри — меньший прямоугольник «обёрнутый объект»;
  - слева в обёртку входит стрелка «вызов»;
  - что происходит со стрелкой, зависит от паттерна:
    - **адаптер** — на границе обёртки стрелка меняет форму (другой цвет и наконечник): «перевод»;
    - **декоратор** — стрелка всегда проходит внутрь; до и после неё — маленькие акцентные метки «до» / «после»;
    - **заместитель** — на границе обёртки «шлагбаум»: стрелка может пройти, а может вернуться назад из самой обёртки;
    - **компоновщик** — стрелка разветвляется на несколько внутренних прямоугольников, у одного из них внутри такие же вложенные;
    - **фасад** — одна стрелка входит, внутри расходится к трём-четырём разным прямоугольникам «подсистемы».
  - Один стиль линий и пропорции везде. Появляется пустой на слайде 8, потом в каждом блоке своего паттерна и в итоговых таблицах.
- **Сквозной индикатор — семь паттернов в ряд:** Адаптер · Мост · Компоновщик · Декоратор · Заместитель · Фасад · Легковес. На разделителе каждого блока — крупно, текущий паттерн подсвечен акцентом; в блоке 6 подсвечены сразу Декоратор и Заместитель. В углу всех слайдов блока — уменьшенная версия.
- **Маркеры примеров в углу** — маленькие пиктограммы, чтобы было видно, какой пример продолжается:
  - логи (блок 1) — пиктограмма листа журнала со строками;
  - пульт и приборы (блок 2) — пиктограмма пульта;
  - графический редактор (блок 3) — круг и линия;
  - заказы и коробки (блоки 3 и 7) — коробка;
  - абстрактный сервис `IService` (блоки 4–5) — шестерёнка;
  - игра (блок 8) — мишень.
  - Слайды про ЛР2 и защиту — плашка «ЛР2» акцентным контуром.
- **Иконки:** минимальный набор. Книга = источник из книги Швеца; предупреждающий треугольник = антипример; галочка в круге = правильно; стрелка C++ → C# = сноска; две реплики = дискуссия.
- **Логотипы, обложки книг, стоковые фото, портреты, сгенерированные изображения не использовать.** Аналогии из книги (розетка, одежда, банковский чек, телефонный заказ) — простыми линейными пиктограммами из геометрических фигур, в одном стиле.
- Код-термины в обычном тексте (`ILogStorage`, `Lazy<T>`, `ToArray()`) — моноширинным.
- **Нижний колонтитул:** номер блока и номер слайда внутри блока, например «5.12».

### Слайд 5 — Семь паттернов (D, сетка карточек 4 + 3)
- **Ключевая строка:** порядок на лекции: адаптер, мост, компоновщик, декоратор, заместитель, фасад, легковес.
- Семь карточек: сверху название по-русски и по-английски, ниже однострочник из книги **дословно**, мелким текстом:
  - **Адаптер** (Adapter): Позволяет объектам с несовместимыми интерфейсами работать вместе.
  - **Мост** (Bridge): Разделяет один или несколько классов на две отдельные иерархии — абстракцию и реализацию, позволяя изменять их независимо друг от друга.
  - **Компоновщик** (Composite): Позволяет сгруппировать объекты в древовидную структуру, а затем работать с ними так, если бы это был единичный объект.
  - **Декоратор** (Decorator): Позволяет динамически добавлять объектам новую функциональность, оборачивая их в полезные «обёртки».
  - **Заместитель** (Proxy): Позволяет подставлять вместо реальных объектов специальные объекты-заменители. Эти объекты перехватывают вызовы к оригинальному объекту, позволяя сделать что-то до или после передачи вызова оригиналу.
  - **Фасад** (Facade): Предоставляет простой интерфейс к сложной системе классов, библиотеке или фреймворку.
  - **Легковес** (Flyweight): Позволяет вместить бóльшее количество объектов в отведённую оперативной память за счёт экономного разделения общего состояния объектов между собой, вместо хранения одинаковых данных в каждом объекте.
- Под сеткой источник с иконкой книги: «А. Швец, с. 142–144». Карточки Декоратор и Заместитель стоят рядом и обведены общей тонкой рамкой с подписью «чаще всего путают».

### Слайд 6 — Общий приём (A)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 157]:** Мост, Стратегия и Состояние (а также слегка и Адаптер) имеют схожие структуры классов — все они построены на принципе «композиции», то есть делегирования работы другим объектам. Тем не менее, они отличаются тем, что решают разные проблемы. Помните, что паттерны — это не только рецепт построения кода определённым образом, но и описание проблем, которые привели к данному решению.

### Слайд 7 — Различаем по задаче (C)
- **Ключевая строка:** по коду обёртки похожи; различаем по тому, что обёртка делает с вызовом.
- Пункты: «Реализует интерфейс» · «Держит в поле другой объект» · «Остальное решает задача — это главный навык лекции».

### Слайд 8 — Обёртка и вызов (D, первое появление сквозной схемы)
- **Ключевая строка:** весь день будем смотреть, что происходит с этой стрелкой.
- Сквозная схема в базовом виде: обёртка, внутри обёрнутый объект, входящая стрелка «вызов». За границей обёртки стрелка обрывается знаком вопроса.

### Слайд 9 — Композиция: агрегация и ассоциация (A, три плашки)
- **[ОПРЕДЕЛЕНИЕ · курс]:** Композиция — создание одних типов, на основе других, используя хранение их данных, как непосредственную часть описываемого объекта (композитный – состоящий из нескольких частей).
- **[ОПРЕДЕЛЕНИЕ · курс]:** При агрегирующей композиции, значения получаются извне, их время жизни никак не привязано к объекту, частью которого они являются.
- **[ОПРЕДЕЛЕНИЕ · курс]:** При ассоциативной композиции значения создаются непосредственно при инициализации объекта, соответственно, время жизни таких объектов привязано к объекту, частью которого они являются.
- Строка над плашками мелко: «повтор лекции 1».

### Слайд 10 — Откуда обёртка берёт объект (D)
- **Ключевая строка:** передали снаружи — агрегация; создала сама — ассоциация; оба случая — композиция.
- Две схемы рядом:
  - слева: объект создаётся снаружи, стрелка «в конструктор» ведёт внутрь обёртки — подпись «агрегация»;
  - справа: объект рождается внутри обёртки, вокруг него пунктир «живёт, пока живёт обёртка» — подпись «ассоциация».
- Над обеими — общая скобка «композиция».

### Слайд 11 — Книга и курс: слова про связи (F)
- **Ключевая строка:** читая книгу, помните — на курсе эти слова устроены иначе.
- Колонка «Книга Швеца» (с. 20–21): «Ассоциация, композиция и агрегация — три отдельных вида отношений» · «“Композиция” в книге — владение временем жизни».
- Колонка «Курс»: «Композиция — общее понятие» · «Её виды — агрегация (значения извне) и ассоциация (значения создаются при инициализации)».
- Правило для ЛР2: «На защите — термины лекции 1».

## Блок 1. Адаптер (слайды 12–32)

### Слайд 12 — Разделитель «1 · Адаптер»

### Слайд 13 — Адаптер (A + мини-схема справа)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 145]:** Адаптер — это структурный паттерн проектирования, который позволяет объектам с несовместимыми интерфейсами работать вместе.
- Строка под плашкой: «Также известен как “Обёртка”».
- Мини-схема справа: пиктограмма вилки и розетки разной формы, между ними переходник. Подпись мелко: «аналогия книги, с. 148–149».

### Слайд 14 — Роли: клиент и клиентский интерфейс (A, две плашки)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 150]:** Клиент — это класс, который содержит существующую бизнес-логику программы.
- **[ОПРЕДЕЛЕНИЕ · книга, с. 150]:** Клиентский интерфейс описывает протокол, через который клиент может работать с другими классами.

### Слайд 15 — Роли: сервис и адаптер (A, две плашки)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 150]:** Сервис – это какой-то полезный класс, обычно сторонний. Клиент не может использовать этот класс напрямую, так как сервис имеет непонятный ему интерфейс.
- **[ОПРЕДЕЛЕНИЕ · книга, с. 150]:** Адаптер — это класс, который может одновременно работать и с клиентом, и с сервисом. Он реализует клиентский интерфейс и содержит ссылку на объект сервиса.

### Слайд 16 — Имена ролей в книге и в курсе (D, таблица 3 строки)
- **Ключевая строка:** в документации и коде встречаются оба набора имён.

| Книга | Курс (и GoF) | Что это |
|---|---|---|
| Клиентский интерфейс | `Target` — целевой интерфейс | абстракция, через которую система хочет работать |
| Сервис | `Adaptee` — адаптируемый тип | тип, который этот интерфейс не реализует |
| Адаптер | `Adapter` — тип-обёртка | реализует `Target`, держит `Adaptee`, переводит вызовы |

- Справа от таблицы — сквозная схема в варианте **адаптера**: на границе обёртки стрелка меняет форму, подпись «перевод».

### Слайд 17 — Кого адаптируют (C)
- **Ключевая строка:** адаптер даёт полиморфизм типам, которые не лежат в одной иерархии.
- Пункты: «`Adaptee` — чаще всего тип сторонней библиотеки» · «Или свой инфраструктурный тип, в который не хотим тащить чужой интерфейс» · «Обёртки — склеивающая прослойка между интерфейсами».

### Слайд 18 — Задача: хранить логи (D, пиктограмма журнала)
- **Ключевая строка:** хранилище будет меняться, а писать его самим не будем — есть готовые библиотеки.
- Схема: «наш код» → `ILogStorage` → две ветки: «Postgres-библиотека» и «Elastic-библиотека». Между `ILogStorage` и каждой библиотекой — пустая рамка со знаком вопроса «как подключить?».

### Слайд 19 — Сторонние типы (B, пиктограмма журнала)
- **Ключевая строка:** эти классы чужие — менять их мы не можем.
- Код:
```csharp
public class PostgresLogStorage
{
    public void Save(string message, DateTime timeStamp, int severity) { ... }
}

public class ElasticSearchLogStorage
{
    public void Save(ElasticLogMessage message) { ... }
}

public record ElasticLogMessage(string Level, string Message, DateTimeOffset Timestamp);
```
- Справа: «Postgres хочет три параметра и `int`» · «Elastic хочет свой объект-сообщение».

```csharp
        if (_userInfoProvider.GetUserInfo().IsAuthenticated)
            _service.DoOperation(args);
    }
}
```

### Слайд 94 — Вопрос к этому коду (C, предупреждающая рамка)
- **Ключевая строка:** пользователь не авторизован — что узнает вызывающий код? Ничего.
- Пункты: треугольник — «Метод молча вернётся, будто операция прошла» · «Бросить исключение? Отказ — ожидаемый сценарий, а исключения для бизнес-ошибок не используем (Don't 22)» · галочка — «Заложить отказ в контракт — Result-тип из лекции 4».

### Слайд 95 — Отказ как часть контракта (B, пиктограмма шестерёнки)

### Слайд 96 — Заместитель с Result-типом (B, пиктограмма шестерёнки)

### Слайд 98 — Кеширующий заместитель (B, пиктограмма шестерёнки)
- **Ключевая строка:** при попадании в кеш сервис не вызывается вовсе — декоратор так не может.
- Код (подсветить акцентным строку `return result;`):
```csharp
public class CachingServiceProxy : IService
{
    private readonly IService _service;
    private readonly Dictionary<OperationArgs, OperationResult> _cache = new();

    public CachingServiceProxy(IService service)
    {
        _service = service;
    }

    public OperationResult DoOperation(OperationArgs args)
    {
        if (_cache.TryGetValue(args, out var result))
            return result;

        return _cache[args] = _service.DoOperation(args);
    }
}
```
- Сноска: `TryGetValue(args, out var result)` — поиск без исключения: `true` и значение в `result`, если ключ есть, как `find` + проверка `!= end()`. `return _cache[args] = …` — присваивание в C# тоже выражение, как в C++.

## Блок 6. Декоратор или заместитель? (слайды 104–110)

### Слайд 104 — Разделитель «6 · Декоратор или заместитель?»
- Индикатор, подсвечены сразу «Декоратор» и «Заместитель». Строка: «Основа одна — композиция; назначение разное».

### Слайд 105 — В чём путаница (D)
- **Ключевая строка:** структура одинаковая, поэтому многие не знают различий.
- Две сквозные схемы рядом: вариант **декоратора** и вариант **заместителя**. Внешне — одинаковые прямоугольники; различие только в поведении стрелки.

### Слайд 106 — Три различия (D, таблица 3 строки)
- **Ключевая строка:** декоратор расширяет, заместитель контролирует.

| Критерий | Декоратор | Заместитель |
|---|---|---|
| Вид композиции | всегда агрегация: обёрнутый объект приходит извне, никакого контроля над ним | агрегация или ассоциация: может получить объект извне, а может создать сам (виртуальный заместитель) и управлять им |
| Вызов обёрнутого | **Extended Dispatch:** только добавляет поведение, вызов не блокирует никогда | **Controlled Dispatch:** может заблокировать вызов или заменить его возвратом кешированных данных |
| Наличие обёрнутого объекта | всегда есть | может не быть (удалённый заместитель) |

### Слайд 107 — Что говорит книга (A, две плашки)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 157, 203, 242]:** Адаптер предоставляет классу альтернативный интерфейс. Декоратор предоставляет расширенный интерфейс. Заместитель предоставляет тот же интерфейс.
- **[ОПРЕДЕЛЕНИЕ · книга, с. 205]:** Декоратор и Заместитель имеют похожие структуры, но разные назначения. Они похожи тем, что оба построены на композиции и делегировании работы другому объекту. Паттерны отличаются тем, что Заместитель сам управляет жизнью сервисного объекта, а обёртывание Декораторов контролируется клиентом.

### Слайд 108 — Итог сравнения (C)
- **Ключевая строка, крупно на половину слайда:** «Декоратор — про расширение логики без изменения существующей. Заместитель — про контроль над обёрнутым объектом».
- Строка ниже: «Удалённое выполнение — одна из вариаций заместителя, на деле самая популярная».

### Слайд 109 — Кто это? (E + таблица без ответов, плашка «ЛР2»)
- Вопрос: «Декоратор или заместитель?»
- Таблица из одного столбца, шесть строк, у всех обёрток тот же интерфейс, что у сервиса:
  1. Пишет в лог аргументы и вызывает сервис.
  2. Замеряет время вызова.
  3. Возвращает сохранённый результат, если такие аргументы уже были.
  4. Не пускает неавторизованного пользователя.
  5. Создаёт сервис при первом вызове.
  6. При ошибке повторяет вызов до трёх раз.
- Подсказка: «Может ли обёртка не вызвать сервис — или вызвать его не один раз?»

### Слайд 110 — Ответы (D, таблица 6 строк)
- **Ключевая строка:** повтор выглядит как добавка, но решает, сколько раз пойдёт вызов, — это контроль.

| Обёртка | Ответ | Почему |
|---|---|---|
| Пишет в лог аргументы и вызывает сервис | декоратор | только добавляет «до» |
| Замеряет время вызова | декоратор | добавляет «до» и «после» |
| Возвращает сохранённый результат | заместитель | может не вызвать сервис |
| Не пускает неавторизованного | заместитель | может заблокировать вызов |
| Создаёт сервис при первом вызове | заместитель | управляет жизнью сервиса |
| Повторяет вызов до трёх раз | заместитель | решает, сколько раз вызвать |

- Слово «декоратор» в столбце ответов — акцентным цветом, «заместитель» — тёмно-серым полужирным (не предупреждающим: это не ошибка).

### Слайд 130 — Легковес неизменяем (A + строка)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 222]:** Так как объекты легковесов будут использованы в разных контекстах, вы должны быть уверены в том, что их состояние невозможно изменять после создания. Всё внутреннее состояние легковес должен получать через параметры конструктора. Он не должен иметь сеттеров и публичных полей.

### Слайд 131 — Считаем (D, таблица 4 строки, пиктограмма мишени)
- **Ключевая строка:** 24 ГБ против 768 КБ.

| | Без легковеса | С легковесом |
|---|---|---|
| Объектов на поле | 100 000 | 100 000 |
| Тяжёлые данные (текстура + модель) | у каждого своя копия, ≈ 256 КБ | 3 общих объекта — по одному на вид |

- Мелко: «256 КБ — условная цифра; важен порядок · пример курса и книги, с. 218».

### Слайд 132 — Легковес и контекст (B, пиктограмма мишени)
- **Ключевая строка:** вид — общий и неизменяемый, у каждого объекта — только своё и ссылка на вид.
- Код (подсветить акцентным строку `public sealed record BulletKind(string Name, Texture Texture, Mesh Mesh);`):
```csharp
public sealed class Texture { ... }

public sealed class Mesh { ... }

public sealed record BulletKind(string Name, Texture Texture, Mesh Mesh);

public readonly record struct Position(float X, float Y, float Z);

public readonly record struct Velocity(float X, float Y, float Z);

public sealed record Bullet(BulletKind Kind, Position Position, Velocity Velocity);
```
- Справа: «`BulletKind` — легковес, внутреннее состояние» · «`Bullet` — контекст, внешнее состояние».
- Сноска: `readonly record struct` — неизменяемый тип-значение: копируется целиком, как `struct` в C++, не создаёт отдельного объекта в куче.

### Слайд 134 — Кеширующая фабрика (B, пиктограмма мишени)
- **Ключевая строка:** уже созданный вид отдаём повторно, новый — грузим один раз.
- Код (подсветить акцентным строку `return kind;`):
```csharp
public class CachingBulletKindFactory : IBulletKindFactory
{
    private readonly IAssetLoader _assets;
    private readonly Dictionary<string, BulletKind> _cache = new();

    public CachingBulletKindFactory(IAssetLoader assets)
    {
        _assets = assets;
    }

    public BulletKind Get(string name)
    {
        if (_cache.TryGetValue(name, out var kind))
            return kind;

        return _cache[name] = new BulletKind(name, _assets.LoadTexture(name), _assets.LoadMesh(name));
    }
}
```
