01

Information Expert

15 минут · Order · OrderItem · Receipt
1 · Information Expert

Формулировка

Информация должна обрабатываться там, где она содержится.
Это значит, что логика выполнения какой-либо операции, должна находиться в типе, содержащем минимально полный набор данных, необходимый для её выполнения.
Прямое следствие инкапсуляции: данные объединяются с теми поведениями, которые им соответствуют.
1 · Information Expert

Модель: заказ и позиции

Заказы содержат позиции; требование — сформировать чек по заказу.
public record OrderItem(int Id, decimal Price, int Quantity);

public class Order
{
    private readonly List<OrderItem> _items;

    public Order()
    {
        _items = new List<OrderItem>();
    }

    public IReadOnlyCollection<OrderItem> Items => _items;
}
Для C++-человека: позиционный record — три свойства только для чтения и конструктор одной строкой; decimal — десятичный тип для денег, без ошибок округления double; List наружу отдаётся как IReadOnlyCollection — снаружи только читать (Do 19).
1 · Information Expert Нарушение

Чек считает отдельный сервис

Арифметика позиции и суммы заказа живёт там, где этих данных нет.
public record Receipt(decimal TotalCost, DateTime Timestamp);

public class ReceiptService
{
    public Receipt CalculateReceipt(Order order)
    {
        var totalCost = order.Items.Sum(item => item.Price * item.Quantity);
        var timestamp = DateTime.Now;

        return new Receipt(totalCost, timestamp);
    }
}
Для C++-человека: Sum(item => …) — LINQ; item => … это лямбда, как [](auto item){…}; Sum пройдёт по коллекции и сложит результаты.
1 · Information Expert

Чем это плохо

SRP
Сервис отвечает за все расчёты в системе.
Дубли
Логика прибита к операции «чек». Понадобилась сумма заказа в другом месте — копируем или тянем сервис туда, где он не нужен по смыслу.
Тесты
Стоимость позиции и заказа нельзя проверить изолированно — эти тесты становятся частью тестов ReceiptService.
1 · Information Expert Исправление

Логика — у владельца данных

public record OrderItem(int Id, decimal Price, int Quantity)
{
    public decimal Cost => Price * Quantity;
}

public class Order
{
    private readonly List<OrderItem> _items;

    public Order() => _items = new List<OrderItem>();

    public IReadOnlyCollection<OrderItem> Items => _items;

    public decimal TotalCost => _items.Sum(x => x.Cost);
}
Для C++-человека: у record может быть тело — как у класса; Cost — вычисляемое свойство, как DistanceFromStart на лекции 1.
1 · Information Expert · вопрос в зал
Почему Cost не в Order? Он же хранит позиции.
«Там, где содержится» — не «в самом большом контейнере», а «в самом маленьком типе, которому хватает данных».
1 · Information Expert

Сервис после исправления

Сервис остался — но теперь он про чек, а не про арифметику.
public record Receipt(decimal TotalCost, DateTime Timestamp);

public class ReceiptService
{
    public Receipt CalculateReceipt(Order order)
    {
        var totalCost = order.TotalCost;
        var timestamp = DateTime.Now;

        return new Receipt(totalCost, timestamp);
    }
}
Запомнить этот тип: в блоке 6 он окажется примером Pure Fabrication.

02

Creator

17 минут · разбор в три шага · и подводные камни
2 · Creator

Каноническая формулировка

Принцип создатель гласит о том, что ответственность за создание используемых объектов должна лежать на типах, их использующих.
Зачем: усиливает сокрытие реализации — потребители типа не завязаны на типы, которые он использует.
Самый неоднозначный принцип GRASP. Две трети блока — о том, где он вредит.
2 · Creator

Задача: добавить позицию в заказ

Первое, что приходит в голову — метод, принимающий готовую позицию.
public class Order
{
    private readonly List<OrderItem> _items;

    // ...

    public Order AddItem(OrderItem item)
    {
        _items.Add(item);
        return this;
    }
}
Для C++-человека: метод возвращает this — чтобы вызовы можно было писать цепочкой: order.AddItem(…).AddItem(…).
2 · Creator · шаг 1 Нарушение

Сервис создаёт позиции сам

Магазин с агрессивной стратегией продаж сразу наполняет заказ продвигаемыми позициями.
public class OrderService
{
    public Order CreateDefaultOrder()
    {
        var order = new Order()
            .AddItem(new OrderItem(1, 100, 1))
            .AddItem(new OrderItem(2, 1000, 3));

        return order;
    }
}
Ненужная связанность OrderService ↔ OrderItem: для передачи информации в заказ этот тип сервису не нужен.
2 · Creator · шаг 2 Соблюдение

Создание переносим внутрь Order

public class Order
{
    private readonly List<OrderItem> _items;

    // ...

    public Order AddItem(
        int id, decimal price, int quantity)
    {
        _items.Add(
            new OrderItem(id, price, quantity));
        return this;
    }
}
public class OrderService
{
    public Order CreateDefaultOrder()
    {
        var order = new Order()
            .AddItem(1, 100, 1)
            .AddItem(2, 1000, 3);

        return order;
    }
}
Сервис больше не знает про OrderItem. Формально — победа.
2 · Creator · шаг 3 Подводные камни

Связанность не исчезла, а стала неявной

Теперь вся реализация зависит от того, какие данные лежат в OrderItem.
Добавилось свойство → меняем сигнатуру Order.AddItem, его реализацию и все типы, которые его вызывают.
Связаны все три типа и потенциально все, кто собирает заказ.
Вопрос в зал: в шаге 1 при добавлении свойства менялись только строки создания — связанность была явной и локальной.
2 · Creator

Можно ли починить

Вариант
Дать Order зависимость, через которую он сам достанет недостающие данные.
Код-потребитель Order не меняется, кроме мест создания Order;

спойлер: это решают порождающие паттерны, которые мы будет разбирать на следующей лекции
Цена: новая зависимость — новая ответственность, риск нарушить SRP, изоляция типа в тестах хуже.
Честно про пример
Он, как и большинство примеров на Creator, искусственный.
В реальности данные не заданы константами в коде — они приходят извне: сетевой запрос, БД.
Чтобы не нарушать изоляцию доменной модели, их маппят в доменные типы снаружи: на вход модели подаются готовые объекты.
2 · Creator

Во что это превращается в реальности

public class OrderService
{
    public Order CreateDefaultOrder(
        IEnumerable<OrderItem> items)
    {
        var order = new Order()
            .AddItem(1, 100, 1)
            .AddItem(2, 1000, 3);

        foreach (var item in items)
        {
            order.AddItem(
                item.Id, item.Price, item.Quantity);
        }

        return order;
    }
}
Лишний код на деконструкцию — и та же проблема при изменении модели.
Неявное ухудшение производительности: разбираем объект и создаём новый, идентичный старому.
Итог: неудобный интерфейс абстракции заказа, который ещё и медленнее.
Удобен разве что в тестах — что почти нивелирует его пользу.
2 · Creator

Вывод: 

Тип, должен отвечать за создание объектов, если обладает достаточной для этого информацией.
То же «минимально полный набор данных», что и в Information Expert, только про создание.

Controller

10 минут · три подвида и две крайности
3 · Controller

Формулировка

Данный паттерн развивает идеи инкапсуляции и сокрытия, путём предоставления единой точки доступа к какой-либо логике системы.
По своей сути, контроллер не содержит какую-то бизнес логику, он является маршрутизатором вызовов, скрывающим реализацию системы от компонентов её визуального представления.
Do 12: разделять бизнес-логику и логику работы с UI.
3 · Controller · подвид 1 из 3

Use-case controller

Use-case controller — контроллер, инкапсулирующий логику обработки какого-то конкретного запроса/события.
public class AddUserController
{
    private readonly IUserService _userService;

    // ...

    public void AddUser(User user)
    {
        _userService.AddUser(user);
    }
}
Подвиды различаются числом охватываемых операций.
3 · Controller · подвид 2 из 3

Use-case group controller

Use-case group controller — контроллер, инкапсулирующий логику обработки группы запросов/событий, логически связных друг с другом.
public class UserController
{
    private readonly IUserService _userService;

    // ...

    public void AddUser(User user)
    {
        _userService.AddUser(user);
    }

    public void DeleteUser(UserId id)
    {
        _userService.DeleteUser(id);
    }
}
Для C++-человека: UserId — свой тип для идентификатора вместо int (Don't 23 с лекции 1).
3 · Controller · подвид 3 из 3

Facade controller

Facade controller — контроллер, скрывающий за собой систему полностью, предоставляющий доступ ко всем операциям, которые она поддерживает.
public class FacadeController
{
    private readonly IUserService
        _userService;
    private readonly IMailingService
        _mailingService;

    // ...
}
Чем шире охват, тем ближе к следующему слайду — к «жирному» контроллеру.
3 · Controller

Две крайности

Контроллер на каждую операцию
Чрезмерная декомпозиция: кодовая база обрастает мелкими типами-пустышками, а у слоя представления становится много зависимостей.
Один контроллер на всю систему
«Fat controllers»: растёт вместе с числом операций и открывает доступ ко всем сразу — нарушение ISP со всеми последствиями.
Середина — group controller: одна логическая группа операций. Группируем по тому же признаку, что в SRP — одно бизнес-требование.

Low Coupling и High Cohesion

16 минут · DataProvider · DataMonitor
4 · Low Coupling и High Cohesion

Два слова, которые путают

coupling
от «связь» — связи между типами
cohesion
от «связно» (говорить связно) — связность внутри типа
Иногда low coupling переводят как «слабое зацепление», чтобы развести понятия.
Совет: оперировать английскими терминами — так недопонимания не будет (Нейминг 3).
4 · Low Coupling и High Cohesion

Формулировки

Достижение низкой связанности между типами, обеспечивает их независимость, что в свою очередь облегчает процесс разработки и тестирования, ведь работать с этими типами можно обособлено друг от друга.
Говорят, что тип имеет высокую связность, если его функционал имеет логическую группировку, допустим, относительно обработки хранимых данных.
High cohesion сильно коррелирует с SRP.
С low coupling мы уже сталкивались напрямую — DIP.
4 · Cohesion Нарушение

Два источника данных в одном типе

public record Measurement(
    double Value, DateTime Timestamp);

public class DataProvider
{
    private readonly HttpClient _httpClient;

    public DataProvider(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }
    public Measurement GetTemperatureData()
    {
        var response = _httpClient
            .GetAsync("temperature-sensor-uri").Result;
        var value = response.Content
            .ReadFromJsonAsync<double>().Result;

        return new Measurement(value, DateTime.Now);
    }

    public Measurement GetUsedMemoryData()
    {
        return new Measurement(
            GC.GetTotalMemory(false), DateTime.Now);
    }
}
В примере вызывается Task.Result вместо оператора await — для облегчения примера полноценное асинхронное взаимодействие отсутствует. Это плохая практика при работе с асинхронным кодом в C#.
4 · Cohesion Исправление

Два независимых типа

public class TemperatureDataProvider
{
    private readonly HttpClient _httpClient;

    public TemperatureDataProvider(
        HttpClient httpClient)
    {
        _httpClient = httpClient;
    }

    public Measurement GetTemperatureData()
    {
        var response = _httpClient
            .GetAsync("temperature-sensor-uri").Result;
        var value = response.Content
            .ReadFromJsonAsync<double>().Result;

        return new Measurement(value, DateTime.Now);
    }
}
public class UsedMemoryDataProvider
{
    public Measurement GetUsedMemoryData()
    {
        return new Measurement(
            GC.GetTotalMemory(false), DateTime.Now);
    }
}
У второго типа нет зависимостей вообще — его можно создать одной строкой в тесте.
4 · Coupling Нарушение

Монитор знает всех провайдеров по именам

public enum MetricType
{
    Temperature,
    UsedMemory,
}

public class DataMonitor
{
    private readonly TemperatureDataProvider
        _temperatureProvider;
    private readonly UsedMemoryDataProvider
        _usedMemoryProvider;

    // ...
    public void Monitor(
        MetricType type,
        CancellationToken token)
    {
        while (token.IsCancellationRequested is false)
        {
            var (value, timestamp) = type switch
            {
                MetricType.Temperature =>
                    _temperatureProvider
                        .GetTemperatureData(),
                MetricType.UsedMemory =>
                    _usedMemoryProvider
                        .GetUsedMemoryData(),
            };

            Console.WriteLine(
                $"{type} = {value}, at {timestamp}");
        }
    }
}
Новый тип провайдера → менять монитор. Это тот же switch по enum, что и на прошлой лекции — OCP.
4 · Coupling Исправление

Абстракция над провайдером

public interface IChronologicalDataProvider
{
    string Kind { get; }

    Measurement GetData();
}
Провайдеры реализуют интерфейс: GetTemperatureData становится GetData, а слово «Temperature» уходит в Kind.
public class DataMonitor
{
    private readonly IChronologicalDataProvider
        _provider;

    public DataMonitor(
        IChronologicalDataProvider provider)
    {
        _provider = provider;
    }

    public void Monitor(CancellationToken token)
    {
        while (token.IsCancellationRequested is false)
        {
            var (value, timestamp) = _provider.GetData();
            Console.WriteLine(
                $"{_provider.Kind} = {value}, at {timestamp}");
        }
    }
}
Этот код можно протестировать, не имея ни одной реализации интерфейса.
4 · Low Coupling и High Cohesion

Coupling и cohesion: две плоскости

Coupling – связи между различными типами, cohesion – связи между логикой в рамках одного типа.
Обе концепции — про упрощение поддержки и универсальность кода, но смотрят на модель в разных плоскостях.

Indirection

8 минут · два вида промежуточного слоя
5 · Indirection

Формулировка

Его суть заключается в том, что модули не должны взаимодействовать напрямую друг с другом, для осуществления взаимодействия используется промежуточный слой.
Направлен на уменьшение связанности. Слой может быть разных видов — их два.
5 · Indirection · вид 1 из 2

Object indirection

Любое взаимодействие с данными, поведениями, модулями, реализованное не напрямую, а через какой-либо агрегирующий их объект – object indirection.
Controller
Объект-посредник между представлением и бизнес логикой
Order.TotalCost
Абстракция над структурой объектов
Proxy (GoF)
Специальный паттерн для решения этой проблемы.

Разберём в следующих лекциях
5 · Indirection · вид 2 из 2

Interface indirection

Любое взаимодействие с данными, поведениями, модулями, реализованное не напрямую, а через какой-либо интерфейс – interface indirection.
Прозрачная подмена

DataMonitor

Декоратор, Прокси (GoF)

10 минут · три коротких принципа
6 · Polymorphism

Polymorphism

Стоит использовать концепцию полиморфизма, вместо ветвления логики основанного на интроспекции типа объекта, либо на каких-то его флаговых атрибутах.
is Bird лекция 2 switch (MetricType) блок 4, сегодня
Don't 6, 7: избегать кастов и down casting. Объектная модель — не просто структуры с методами.
6 · Protected Variations

Protected Variations

В таких случаях стоит выделять стабильный интерфейс, над нестабильной, изменчивой реализацией.
Что делает разработчик
Анализирует требования и определяет, какие из них могут измениться в недалёком будущем.
Оговорка
Не над каждой реализацией нужен интерфейс — Do 21, YAGNI.
6 · Pure Fabrication

Pure Fabrication

Данная концепция подразумевает, что в системе может присутствовать искусственная, выдуманная сущность, не отражающая каких-либо частей моделируемых бизнес-процессов.
Из этой лекции: ReceiptService DataMonitor
Крайне не рекомендуется вносить такие типы в доменную модель: модель, близкая к бизнес-процессам, меняется проще — изменения бизнеса для неё натуральны, для выдуманных сущностей — нет.
Но и один-к-одному с реальностью не нужно: это может расходиться с лучшими практиками разработки и проектирования.
