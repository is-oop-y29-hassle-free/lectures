## 0. GRASP и SOLID: тот же материал под другим углом (6 мин)

**Слайд: зачем второй набор принципов.**

> **Определение (акцент на слайде):** Принципы GRASP достаточно схожи с принципами SOLID в том смысле, что предполагают достижению более простой поддержки кода.

Устно: GRASP сильно коррелирует с SOLID, покрывает почти те же концепции, но смотрит на них под другим углом. SOLID отвечает «как устроить тип», GRASP — «какому типу отдать ответственность». На защите вас будут спрашивать и так, и так.

**Слайд: акроним.** В отличие от SOLID, составлен не из первых букв принципов:

> **Определение (акцент на слайде):** General responsibility assignment software principles – общие принципы распределения ответственностей в ПО.

**Слайд: карта девяти принципов.** В три группы, чтобы не пугать списком:
- **Где лежит ответственность:** Information Expert · Creator · Controller
- **Как измерить, что лежит правильно:** Low Coupling · High Cohesion
- **Как защитить от изменений:** Indirection · Polymorphism · Protected Variations · Pure Fabrication

Сказать: первые пять — с кодом на одном сквозном примере; последние четыре короткие и во многом уже знакомы по SOLID.

**Слайд: сквозной пример.** Система учёта покупок: `Order`, `OrderItem`, чек `Receipt`; во второй половине — сбор метрик: `DataProvider`, `DataMonitor`. Все примеры лекции — про них.

## 1. Information Expert (15 мин)

**Слайд: формулировка.**

> **Определение (акцент на слайде):** Информация должна обрабатываться там, где она содержится.

> **Определение (акцент на слайде):** Это значит, что логика выполнения какой-либо операции, должна находиться в типе, содержащем минимально полный набор данных, необходимый для её выполнения.

Связка с лекцией 1: это прямое следствие инкапсуляции — объединяем данные именно с теми поведениями, которые им соответствуют.

**Слайд: модель.** Заказы содержат позиции; требование — сформировать чек по заказу.
```csharp
public record OrderItem(int Id, decimal Price, int Quantity);

public class Order
{
    private readonly List<OrderItem> _items;

    public Order()
    {
        _items = new List<OrderItem>();
    }

    public IReadOnlyCollection<OrderItem> Items => _items;
}
```
*Для C++-человека:* `record OrderItem(int Id, decimal Price, int Quantity)` — позиционная запись: три свойства только для чтения и конструктор одной строкой; `decimal` — десятичный тип для денег, без ошибок округления `double`; `List<T>` наружу отдаётся как `IReadOnlyCollection<T>` — снаружи только читать (Do 19).

**Слайд: нарушение.** Чек считает отдельный сервис:
```csharp
public record Receipt(decimal TotalCost, DateTime Timestamp);

public class ReceiptService
{
    public Receipt CalculateReceipt(Order order)
    {
        var totalCost = order.Items.Sum(item => item.Price * item.Quantity);
        var timestamp = DateTime.Now;

        return new Receipt(totalCost, timestamp);
    }
}
```
*Для C++-человека:* `Sum(item => …)` — LINQ: `item => …` — лямбда, как `[](auto item){…}`; `Sum` пройдёт по коллекции и сложит результаты.

> В авторском файле параметр назван `Order customer`, а элемент в лямбде — `order`. В плане переименовано в `order` / `item`: иначе на слайде «заказ» называется покупателем, а «позиция» — заказом, и это прямое нарушение правила нейминга (Нейминг 1). Проверить на слайдах.

Разбор: модель данных предметной области соответствует, а распределение логики — нет. Вся арифметика — и стоимость позиции, и сумма по заказу — в сервисе, у которого этих данных нет; он их выпрашивает.

**Слайд: чем это плохо.** Три следствия:
- **Нарушение SRP** — сервис отвечает за все расчёты в системе.
- **Дублирование** — логика прибита к операции «чек»; понадобилась сумма заказа в другом месте — либо копируем, либо тянем `ReceiptService` туда, где связь с ним не имеет смысла с точки зрения предметной области. Плюс транзитивные зависимости в тестах.
- **Тестирование** — нельзя изолированно проверить стоимость позиции или заказа; эти тесты становятся частью тестов `ReceiptService`.

**Слайд: исправление.** Соблюсти SRP и распределить ответственность по типам, хранящим информацию:
```csharp
public record OrderItem(int Id, decimal Price, int Quantity)
{
    public decimal Cost => Price * Quantity;
}

public class Order
{
    private readonly List<OrderItem> _items;

    public Order()
    {
        _items = new List<OrderItem>();
    }

    public IReadOnlyCollection<OrderItem> Items => _items;

    public decimal TotalCost => _items.Sum(x => x.Cost);
}
```
*Для C++-человека:* у `record` может быть тело — как у класса; `Cost` — вычисляемое свойство, как `DistanceFromStart` на лекции 1.

**Слайд: «минимально полный набор».** Вопрос в зал: «Почему `Cost` не в `Order`? Он же хранит позиции». Ответ авторский: `Order` хранит позиции, но не обладает минимальным набором данных по ним — минимально полный набор для стоимости позиции лежит в `OrderItem`. «Там, где содержится» — не «в самом большом контейнере», а «в самом маленьком типе, которому хватает данных».

**Слайд: сервис после исправления.**
```csharp
public record Receipt(decimal TotalCost, DateTime Timestamp);

public class ReceiptService
{
    public Receipt CalculateReceipt(Order order)
    {
        var totalCost = order.TotalCost;
        var timestamp = DateTime.Now;

        return new Receipt(totalCost, timestamp);
    }
}
```
Разбор: сервис остался — но теперь он про чек, а не про арифметику. Запомнить `ReceiptService`: в блоке 6 он окажется примером Pure Fabrication.

**Как найти у себя.**
1. Есть ли метод, который берёт у объекта три свойства и что-то из них считает? Этот расчёт просится внутрь объекта.
2. Есть ли «сервис», который знает про внутренности модели больше, чем сама модель?
3. Самое частое в ЛР1: цикл по `order.Items` снаружи `Order`.

## 2. Creator — и его подводные камни (17 мин)

Самый неоднозначный принцип GRASP: авторский текст на две трети — про то, где он вредит. Разбор в три шага; на слайдах шаги не смешивать.

**Слайд: формулировка (каноническая).**

> **Определение (акцент на слайде):** Принцип создатель гласит о том, что ответственность за создание используемых объектов должна лежать на типах, их использующих.

Зачем: усиливает сокрытие реализации — потребители типа не завязаны на типы, которые он использует; меньше связанность.

**Слайд: задача.** В систему покупок нельзя добавить позицию. Первое, что приходит в голову — метод, принимающий `OrderItem`:
```csharp
public class Order
{
    private readonly List<OrderItem> _items;

    ...

    public Order AddItem(OrderItem item)
    {
        _items.Add(item);
        return this;
    }
}
```
*Для C++-человека:* метод возвращает `this` — чтобы вызовы можно было писать цепочкой: `order.AddItem(…).AddItem(…)`.

**Шаг 1 — нарушение.** Магазин с агрессивной стратегией продаж сразу наполняет заказ продвигаемыми позициями:
```csharp
public class OrderService
{
    public Order CreateDefaultOrder()
    {
        var order = new Order()
            .AddItem(new OrderItem(1, 100, 1))
            .AddItem(new OrderItem(2, 1000, 3));

        return order;
    }
}
```
Разбор: `OrderService` завязан на тип `OrderItem`, хотя для передачи информации в заказ этот тип ему не нужен. Ненужная связанность `OrderService` ↔ `OrderItem`.

**Шаг 2 — соблюдение.** Переносим создание `OrderItem` в `Order`:
```csharp
public class Order
{
    private readonly List<OrderItem> _items;

    ...

    public Order AddItem(int id, decimal price, int quantity)
    {
        _items.Add(new OrderItem(id, price, quantity));
        return this;
    }
}
```
```csharp
public class OrderService
{
    public Order CreateDefaultOrder()
    {
        var order = new Order()
            .AddItem(1, 100, 1)
            .AddItem(2, 1000, 3);

        return order;
    }
}
```
Разбор: `OrderService` больше не знает про `OrderItem`. Формально — победа.

**Шаг 3 — подводные камни.** Авторский поворот: мы добавили новую, более страшную связанность — страшную тем, что она неявная. Теперь вся реализация зависит от того, какие данные лежат в `OrderItem`. Добавилось свойство → меняем сигнатуру `Order.AddItem`, его реализацию и все типы, которые его вызывают. Связаны все три типа и потенциально все, кто собирает заказ.

Вопрос в зал: «В шаге 1 при добавлении свойства в `OrderItem` что менялось?» — только те строки, где он создаётся. Связанность была явной и локальной.

**Слайд: можно ли починить.** Авторские варианты, каждый с ценой:
- Дать `Order` зависимость, через которую он сам достанет недостающие данные, — код-потребитель `Order` не меняется (кроме мест создания `Order`; это решает порождающий паттерн Фабрика — ЛР3). Но: новая зависимость — новая ответственность у `Order` (как, если честно, и само создание `OrderItem`), риск дойти до нарушения SRP, и тестирование хуже — изоляция типа нарушена.
- Честно про пример: он, как и большинство примеров на Creator в разных источниках, искусственный. В реальности данные не заданы константами в коде — они приходят извне (сетевой запрос, БД), и, чтобы не нарушать изоляцию доменной модели, их маппят в доменные типы снаружи: на вход модели подаются готовые объекты.

**Слайд: во что это превращается в реальности.**
```csharp
public class OrderService
{
    public Order CreateDefaultOrder(IEnumerable<OrderItem> items)
    {
        var order = new Order()
            .AddItem(1, 100, 1)
            .AddItem(2, 1000, 3);

        foreach (var item in items)
        {
            order.AddItem(item.Id, item.Price, item.Quantity);
        }

        return order;
    }
}
```
Разбор: кроме лишнего кода на деконструкцию `OrderItem` (и той же проблемы при изменении модели) — неявное ухудшение производительности: разбираем объект и создаём новый, идентичный старому. Итог: неудобный интерфейс абстракции заказа, который ещё и медленнее. Удобен разве что в тестах — что почти нивелирует его пользу.

**Слайд: вывод по Creator.** Использовать с осторожностью, анализируя не только текущие, но и возможные использования: избавившись от связанности «создаваемый объект ↔ тип, использующий абстракцию создателя» (в большинстве случаев — чисто синтаксической), можно причинить модели более серьёзный вред. Отсюда — авторская правка канона:

> **Определение (акцент на слайде):** Тип, должен отвечать за создание объектов, если обладает достаточной для этого информацией.

Связать с Information Expert: то же «минимально полный набор данных», только про создание. И с YAGNI (Do 21): не прячьте создание ради красоты вызова.

**Как найти у себя.**
1. Метод `AddX(int, string, decimal, …)` с четырьмя и более примитивами — это разобранный объект; спросите, кому на самом деле хватает данных его собрать.
2. Тип создаёт объекты, данные для которых ему передают целиком снаружи? Тогда пусть их передают уже объектами.

## 3. Controller — три подвида и две крайности (10 мин)

**Слайд: формулировка.**

> **Определение (акцент на слайде):** Данный паттерн развивает идеи инкапсуляции и сокрытия, путём предоставления единой точки доступа к какой-либо логике системы.

> **Определение (акцент на слайде):** По своей сути, контроллер не содержит какую-то бизнес логику, он является маршрутизатором вызовов, скрывающим реализацию системы от компонентов её визуального представления.

Устно: в основном — для приложений с интерфейсом: ответственность за взаимодействие с приложением переносится с модулей представления в отдельную сущность. Контроллер принимает запросы пользователя и события UI и диспетчеризует их в модули, которые их обрабатывают. В Do/Don't это **Do 12**: разделять бизнес-логику и логику работы с UI.

**Слайд: три подвида — различаются числом охватываемых операций.** Один слайд на подвид, определение плашкой, код рядом.

> **Определение (акцент на слайде):** Use-case controller — контроллер, инкапсулирующий логику обработки какого-то конкретного запроса/события.
```csharp
public class AddUserController 
{
    private readonly IUserService _userService;

    // ...

    public void AddUser(User user)
    {
            _userService.AddUser(user);
    }
}
```

> **Определение (акцент на слайде):** Use-case group controller — контроллер, инкапсулирующий логику обработки группы запросов/событий, логически связных друг с другом.
```csharp
public class UserController
{
    private readonly IUserService _userService;

    // ...

    public void AddUser(User user)
    {
            _userService.AddUser(user);
    }

    public void DeleteUser(UserId id)
    {
            _userService.DeleteUser(id);
    }
}
```

> **Определение (акцент на слайде):** Facade controller — контроллер, скрывающий за собой систему полностью, предоставляющий доступ ко всем операциям, которые она поддерживает.
```csharp
public class FacadeController
{
		private readonly IUserService _userService;
		private readonly IMailingService _mailingService;

		// ...
}
```
*Для C++-человека:* `UserId` — свой тип для идентификатора вместо `int` (Don't 23 с лекции 1).

**Слайд: две крайности.**
- **Контроллер на каждую операцию** — чрезмерная декомпозиция: кодовая база обрастает мелкими типами-пустышками, а у слоя представления, который обычно охватывает несколько операций, становится много зависимостей.
- **Один контроллер на всю систему** — «fat controllers»: растёт вместе с числом операций и открывает доступ ко всем операциям сразу — нарушение ISP со всеми последствиями с прошлой лекции.
- Середина — group controller: одна логическая группа операций. Вопрос в зал: «По какому признаку группировать?» — по тому же, что и в SRP: одно бизнес-требование.

**Как найти у себя.** В ЛР с консольным интерфейсом: есть ли `Console.ReadLine` и вызов бизнес-логики в одном методе? Между ними должен быть контроллер. И наоборот: есть ли в контроллере `if`-ы про предметную область? Это бизнес-логика, ей там не место.

## 4. Low Coupling и High Cohesion (16 мин)

**Слайд: два слова, которые путают.** Устно: coupling — от «связь», cohesion — от «связно» (говорить связно). Иногда low coupling переводят как «слабое зацепление», чтобы развести понятия. Авторский совет — оперировать английскими терминами, чтобы гарантированно избежать недопонимания (и Нейминг 3 про общепринятые английские термины — из той же логики).

> **Определение (акцент на слайде):** Достижение низкой связанности между типами, обеспечивает их независимость, что в свою очередь облегчает процесс разработки и тестирования, ведь работать с этими типами можно обособлено друг от друга.

> **Определение (акцент на слайде):** Говорят, что тип имеет высокую связность, если его функционал имеет логическую группировку, допустим, относительно обработки хранимых данных.

Связка: high cohesion сильно коррелирует с SRP; с low coupling мы уже сталкивались напрямую — DIP.

**Слайд: low cohesion — нарушение.** Приложению нужно собирать метрики: температуру с удалённого сенсора и объём памяти, используемой приложением. Результат измерения — свой тип:
```csharp
public record Measurement(double Value, DateTime Timestamp);

public class DataProvider
{
    private readonly HttpClient _httpClient;

    public DataProvider(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }

    public Measurement GetTemperatureData()
    {
        var response = _httpClient.GetAsync("temperature-sensor-uri").Result;
        var value = response.Content.ReadFromJsonAsync<double>().Result;

        return new Measurement(value, DateTime.Now);
    }

    public Measurement GetUsedMemoryData()
    {
        return new Measurement(GC.GetTotalMemory(false), DateTime.Now);
    }
}
```
*Для C++-человека:* `Measurement` — свой тип результата вместо пары значений (Don't 8: кортежи в сигнатурах не используем); `HttpClient` — HTTP-запросы из стандартной библиотеки; `GC.GetTotalMemory` — спросить у сборщика мусора, сколько занято.

Оговорка на слайде мелким текстом (авторская, повторять под каждым сниппетом с `HttpClient`): в примере используется асинхронный метод `HttpClient.GetAsync`. Для облегчения примера полноценное асинхронное взаимодействие отсутствует — вызывается свойство `Task.Result` вместо оператора `await`. Это плохая практика при работе с асинхронным кодом в C#.

Разбор: два несвязанных источника данных в одном типе — нарушение SRP со всеми последствиями. `HttpClient` нужен только температуре, а тащить его придётся всегда.

**Слайд: исправление — два независимых типа.**
```csharp
public class TemperatureDataProvider
{
    private readonly HttpClient _httpClient;

    public TemperatureDataProvider(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }

    public Measurement GetTemperatureData()
    {
        var response = _httpClient.GetAsync("temperature-sensor-uri").Result;
        var value = response.Content.ReadFromJsonAsync<double>().Result;

        return new Measurement(value, DateTime.Now);
    }
}

public class UsedMemoryDataProvider
{
    public Measurement GetUsedMemoryData()
    {
        return new Measurement(GC.GetTotalMemory(false), DateTime.Now);
    }
}
```
(Оговорка про `.Result` — та же.)

Разбор: у `UsedMemoryDataProvider` нет зависимостей вообще — его можно создать одной строкой в тесте.

**Слайд: high coupling — нарушение.** Метрики надо выводить. Наивный монитор:
```csharp
public enum MetricType
{
    Temperature,
    UsedMemory,
}

public class DataMonitor
{
    private readonly TemperatureDataProvider _temperatureProvider;
    private readonly UsedMemoryDataProvider _usedMemoryProvider;

    public DataMonitor(TemperatureDataProvider temperatureProvider, UsedMemoryDataProvider usedMemoryProvider)
    {
        _temperatureProvider = temperatureProvider;
        _usedMemoryProvider = usedMemoryProvider;
    }

    public void Monitor(MetricType type, CancellationToken cancellationToken)
    {
        while (cancellationToken.IsCancellationRequested is false)
        {
            var (value, timestamp) = type switch
            {
                MetricType.Temperature => _temperatureProvider.GetTemperatureData(),
                MetricType.UsedMemory => _usedMemoryProvider.GetUsedMemoryData(),
            };

            Console.WriteLine($"{type} = {value}, at {timestamp}");
        }
    }
}
```
*Для C++-человека:* `var (value, timestamp) = …` — деконструкция `record` в две переменные, как structured binding; позиционный `record` умеет это из коробки; `CancellationToken` — флаг «пора останавливаться», который передают извне; `is false` — то же, что `== false`.

Разбор: монитор зависит от конкретных провайдеров, выбор — через перечисление, которое по сути флаг. Новый тип провайдера → менять монитор (это `switch` по `enum` с прошлой лекции — OCP). Тестировать монитор отдельно от провайдеров нельзя, а у одного из них в зависимостях `HttpClient` — сеть либо усложнит заглушки, либо сведёт модульность теста на нет.

**Слайд: исправление — абстракция над провайдером.**
```csharp
public interface IChronologicalDataProvider
{
    string Kind { get; }

    Measurement GetData();
}

public class DataMonitor
{
    private readonly IChronologicalDataProvider _provider;

    public DataMonitor(IChronologicalDataProvider provider)
    {
        _provider = provider;
    }

    public void Monitor(CancellationToken cancellationToken)
    {
        while (cancellationToken.IsCancellationRequested is false)
        {
            var (value, timestamp) = _provider.GetData();
            Console.WriteLine($"{_provider.Kind} = {value}, at {timestamp}");
        }
    }
}
```
Разбор: сниппет жизнеспособен сам по себе — его можно протестировать, не имея ни одной реализации `IChronologicalDataProvider`. Нужна конкретная метрика — передать провайдера при создании монитора (Do 13); нужно мониторить разные метрики одним объектом — перенести параметр в сигнатуру `Monitor`. Провайдеры при этом должны реализовать интерфейс — `GetTemperatureData` / `GetUsedMemoryData` становятся `GetData` (и слово «Temperature» из имени метода уходит в `Kind` — нейминг).

**Слайд: две плоскости.**

> **Определение (акцент на слайде):** Coupling – связи между различными типами, cohesion – связи между логикой в рамках одного типа.

Обе концепции — про упрощение поддержки и универсальность кода, но смотрят на модель в разных плоскостях.

**Как найти у себя.**
1. Cohesion: есть ли в классе поле, которое использует только один метод из пяти? Вероятно, это другой класс.
2. Coupling: сколько конкретных типов перечислено в конструкторе? Каждый — это тип, без которого класс не протестировать.

## 5. Indirection — два вида (8 мин)

**Слайд: формулировка.**

> **Определение (акцент на слайде):** Его суть заключается в том, что модули не должны взаимодействовать напрямую друг с другом, для осуществления взаимодействия используется промежуточный слой.

Направлен на уменьшение связанности; слой может быть разных видов.

**Слайд: object indirection.**

> **Определение (акцент на слайде):** Любое взаимодействие с данными, поведениями, модулями, реализованное не напрямую, а через какой-либо агрегирующий их объект – object indirection.

Примеры — всё уже видели: Controller из блока 3 (объект-посредник между представлением и системой); `Order.TotalCost` из блока 1 (абстракция над структурой объектов — сервис не лезет в позиции); паттерн GoF «Посредник» — ЛР4.

**Слайд: interface indirection.**

> **Определение (акцент на слайде):** Любое взаимодействие с данными, поведениями, модулями, реализованное не напрямую, а через какой-либо интерфейс – interface indirection.

Развивает полиморфизм: реализации подменяются прозрачно для модулей; тестировать можно без реализации посредника — `DataMonitor` с `IChronologicalDataProvider` из блока 4. Паттерны GoF «Декоратор» и «Прокси» — ЛР2.

**Слайд: сравнение.** Одна схема: два модуля A и B; слева между ними объект-агрегатор (object), справа — интерфейс (interface). Подпись: object — «кто-то стоит между», interface — «между стоит контракт, а кто его выполняет — неважно».

## 6. Polymorphism · Protected Variations · Pure Fabrication (10 мин)

Три коротких принципа; каждому — один слайд с плашкой и один тезис.

**Polymorphism.** «С данным принципом всё до банального просто»: объектная модель — не просто структуры с методами.

> **Определение (акцент на слайде):** Стоит использовать концепцию полиморфизма, вместо ветвления логики основанного на интроспекции типа объекта, либо на каких-то его флаговых атрибутах.

Уже видели дважды: `is Bird` на лекции 2, `switch` по `MetricType` сегодня. Do/Don't: **Don't 6, 7** — избегать кастов и down casting.

**Protected Variations.** Сильно коррелирует с OCP: акцент на потенциальных точках нестабильности. Разработчик анализирует требования и определяет, какие из них могут измениться в недалёком будущем.

> **Определение (акцент на слайде):** В таких случаях стоит выделять стабильный интерфейс, над нестабильной, изменчивой реализацией.

Тезис: поведение модулей меняется передачей других реализаций — как в OCP. И та же оговорка, что и там: «разработчик отличается от программиста» — не над каждой реализацией нужен интерфейс (Do 21, YAGNI).

**Pure Fabrication.**

> **Определение (акцент на слайде):** Данная концепция подразумевает, что в системе может присутствовать искусственная, выдуманная сущность, не отражающая каких-либо частей моделируемых бизнес-процессов.

Обычно это сервисы с инфраструктурной логикой, не отражающие бизнес-концепций: `ReceiptService` и `DataMonitor` из этой лекции. Две оговорки авторские, обе на слайд:
- Крайне не рекомендуется вносить такие типы в доменную модель: модель, близкая к бизнес-процессам, меняется проще — изменения бизнеса для неё натуральны, для выдуманных сущностей — нет. (Это разделение «домен / сервисы» — ЛР5.)
- Но и один-к-одному с реальностью не нужно: это может расходиться с лучшими практиками разработки и проектирования.

## 7. Итоги (8 мин)

**Слайд: GRASP ↔ SOLID.** Таблица соответствий — главный «унести с собой»:

| GRASP | Ближайший SOLID | Общая идея |
|-------|-----------------|------------|
| Information Expert | SRP | логика — у того, у кого данные |
| Creator | SRP (с оговоркой) | создаёт тот, кому хватает информации |
| Controller | SRP + ISP | точка входа без бизнес-логики, не «жирная» |
| High Cohesion | SRP | один тип — одна логическая группа |
| Low Coupling | DIP | зависеть от абстракций |
| Indirection | DIP | между модулями — слой |
| Polymorphism | OCP, LSP | вместо `if` по типу |
| Protected Variations | OCP | стабильный интерфейс над нестабильной реализацией |
| Pure Fabrication | — | сервисы есть, но не в домене |

**Слайд: девять принципов одной фразой.** Сказать: если помнить только одно — GRASP отвечает на вопрос «кому отдать ответственность», и ответ почти всегда — «тому, у кого есть информация».

**Слайд: чек-лист перед PR** — по одному вопросу на группу:
- Есть ли расчёт снаружи объекта, у которого есть все данные? (Information Expert)
- Есть ли `AddX(…)` с пятью примитивами? (Creator)
- Есть ли `Console.ReadLine` и бизнес-логика в одном методе? (Controller)
- Есть ли поле, нужное одному методу из многих? (Cohesion)
- Сколько конкретных типов в конструкторе? (Coupling)
- Есть ли `switch` по типу или флагу? (Polymorphism)

Напомнить: чек-лист — то, чем проверяете себя сами; агент для этого — нарушение силлабуса.

**Слайд: что дальше.** ЛР2 (структурные паттерны) — Декоратор и Прокси как interface indirection; ЛР3 (порождающие) — Фабрика как ответ на подводные камни Creator; ЛР4 — Посредник как object indirection.
