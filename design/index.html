Интерфейс и реализация

Интерфейс — то, что объект обещает внешнему миру: какие поведения у него можно вызвать и что они сделают. Реализация — как он это делает. Пользователь объекта должен знать только интерфейс; реализацию можно заменить, не затронув пользователя.

Минимальный открытый интерфейс

Открытый интерфейс класса должен быть минимальным: давать пользователю ровно то, что ему нужно для работы, и ничего сверх. Всё, что можно скрыть, — скрыть; добавить в интерфейс позже легко, убрать — почти невозможно, потому что на это уже кто-то завязался.

2.6Лекция 4 · Проектирование

CRC-карточка

Статья 1989 года называется „…обучения объектно-ориентированному мышлению“ — как книга Вайсфельда.

CRC-карточка (Class — Responsibilities — Collaborators) — карточка на один класс, где записаны его имя, ответственности (что знает и что умеет) и коллабораторы (с какими классами взаимодействует, чтобы выполнить ответственности). Если ответственности не помещаются на карточку — класс делает слишком много.

Источник: K. Beck, W. Cunningham. A Laboratory For Teaching Object-Oriented Thinking, OOPSLA 1989

Make illegal states unrepresentable

«Make illegal states unrepresentable» — проектировать типы так, чтобы некорректное состояние в принципе нельзя было выразить значением этого типа; тогда проверка переносится из рантайма в компилятор или в единственную точку создания.

Parse, don't validate

«Parse, don't validate» — вместо проверки данных, после которой вызывающий продолжает работать с тем же «сырым» значением, преобразовывать их на границе в тип, который несёт гарантию своей корректности. Проверили один раз — дальше работаем с типом, а не перепроверяем.

Value object в C#

Правило «0–100%» и правило «хватает ли на поездку» — внутри типа.

public readonly record struct BatteryLevel
{
private const int MinimumForRide = 15;
public BatteryLevel(int percent)
{
ArgumentOutOfRangeException.ThrowIfNegative(percent);
ArgumentOutOfRangeException.ThrowIfGreaterThan(percent, 100);
Percent = percent;
}
public int Percent { get; }
public bool IsEnoughForRide => Percent >= MinimumForRide;
}

4.1Лекция 4 · Проектирование

Исключение

Исключение — объект, описывающий ошибку, возникшую при выполнении программы; при выбросе исключения нормальный поток выполнения прерывается, и управление передаётся ближайшему подходящему обработчику вверх по стеку вызовов. В .NET все исключения наследуются от System.Exception и несут стек вызовов в момент выброса.

Источник: Microsoft Learn. Handling and throwing exceptions in .NET

Классификация Липперта

Классификация исключений Эрика Липперта (одного из разработчиков компилятора C#): фатальные (не ваша вина, обработать нельзя), глупые (ваша ошибка в коде — исправлять код, а не ловить), досадные (результат неудачного дизайна API, бросающего исключение в неисключительной ситуации), внешние (реальность за пределами программы — ловить и обрабатывать).

4.8Лекция 4 · Проектирование

Три вида ошибок по Влашину

Скотт Влашин делит ошибки на три вида: доменные ошибки — ожидаемые исходы, которые являются частью бизнес-процесса и о которых знает заказчик («отказано в поездке»); паники — ошибки, после которых система в неизвестном состоянии (баг, нехватка памяти); инфраструктурные — отказ внешнего мира (сеть, диск). Доменные ошибки моделируются как значения; паники — исключения; инфраструктурные — по ситуации.

Источник: S. Wlaschin. Against Railway-Oriented Programming, 2019

Result type

Result type — тип возвращаемого значения, который явно кодирует взаимоисключающие исходы операции: успех со значением или неуспех с причиной. Исход виден в сигнатуре, и чтобы получить значение, вызывающий обязан разобрать оба варианта.

Источник: S. Wlaschin. Railway Oriented Programming, 2014

Discriminated union

Discriminated union (размеченное объединение) — тип, значение которого — ровно один из заранее известного конечного набора вариантов, и каждый вариант может нести свои данные. Result — частный случай с двумя вариантами.

Источник: Microsoft Learn. Discriminated Unions (F#)

В C# 14 union-типов нет — собираем из record

Приватный конструктор базы — и набор вариантов закрыт.

public abstract record RideStartResult
{
private RideStartResult() { }
public sealed record Started(Ride Ride) : RideStartResult;
public sealed record Rejected(RideRejectionReason Reason) : RideStartResult;
}
public abstract record RideRejectionReason
{
private RideRejectionReason() { }
public sealed record LowBattery(BatteryLevel Actual) : RideRejectionReason;
public sealed record InsufficientBalance(decimal Balance) : RideRejectionReason;
}

Операция возвращает результат

Два guard clause в начале — и два исхода в сигнатуре.

public sealed class RentalService
{
public RideStartResult StartRide(Rider rider, Scooter scooter, Tariff tariff, DateTimeOffset startedAt)
{
if (scooter.Battery.IsEnoughForRide is false)
{
return new RideStartResult.Rejected(new RideRejectionReason.LowBattery(scooter.Battery));
}
if (rider.CanPay is false)
{
return new RideStartResult.Rejected(new RideRejectionReason.InsufficientBalance(rider.Balance));
}
return new RideStartResult.Started(new Ride(rider, scooter, tariff, startedAt));
}
}
Guard clauses — Do 14
CanPay, IsEnoughForRide — правила у тех, у кого данные
Время — аргументом, не Now внутри: иначе не протестировать (Do 13)

Тест на Result

Проверяем причину отказа и её данные, а не только факт отказа.

[Fact]
public void StartRide_LowBattery_ReturnsRejectedWithReason()
{
// Arrange
var rider = new Rider("Ann", balance: 100m);
var scooter = new Scooter("SC-1", new BatteryLevel(10));
var service = new RentalService();
// Act
var result = service.StartRide(rider, scooter, new Tariff(5m), DateTimeOffset.UtcNow);
// Assert
var rejected = Assert.IsType<RideStartResult.Rejected>(result);
var lowBattery = Assert.IsType<RideRejectionReason.LowBattery>(rejected.Reason);
Assert.Equal(10, lowBattery.Actual.Percent);
}

Vertical Slice Architecture

Vertical Slice Architecture — организация кода вокруг отдельных запросов (фич) системы, а не технических слоёв: каждый срез содержит всё, что нужно для одной фичи, от входа до хранения. Принцип: минимизировать связность между срезами и максимизировать связность внутри среза.

Источник: J. Bogard. Vertical Slice Architecture, 2018

Screaming Architecture

Screaming Architecture — структура проекта должна «кричать» о предметной области, а не о фреймворке: глядя на папки верхнего уровня, должно быть понятно, что делает система, а не на чём она написана.

Источник: R. C. Martin (en.wikipedia.org/wiki/Robert_C._Martin). Screaming Architecture, 2011

Три вещи унести

По одной на каждый вопрос проектирования.

1
Проектирование начинается с текста задачи: существительные → классы, глаголы → ответственности, CRC-карточки → проверка сценарием
2
Об ошибке спросить: знает ли заказчик? Знает — результат. Баг — исключение, не ловить, а исправлять. Внешний мир — ловить на границе
3
Одно изменение требований — одно место: класс, папка или срез
