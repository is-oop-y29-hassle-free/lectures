Два вида полиморфизма в одном вызове

double dispatching

  • диспетчеризация – передача потока выполнения другому методу
  • используется два вида полиморфизма
    • динамический, чтобы вызвать Accept
    • статический, чтобы вызвать нужную перегрузку Visit
component.Accept(visitor)→ виртуальный вызов:
какой узел?→ FileFileSystemComponent.Accept→ перегрузка выбрана компилятором:
this — файл
↓ visitor.Visit(FileFileSystemComponent)→ виртуальный вызов:
какой визитор?→ FormattingVisitor.Visit(…)

Для C++-человека: в C++ то же самое делают так же, вручную; для std::variant есть std::visit. Перегрузка выбирается на этапе компиляции по статическому типу аргумента — поэтому Accept нужен в каждом классе узла, а не один раз в базовом.

Визитор сам обходит дерево и копит результат в полях

реализация: FormattingVisitor

public sealed class FormattingVisitor : IFileSystemComponentVisitor
{
    private readonly StringBuilder _builder = new();
    private int _padding;

    public string Value => _builder.ToString();

    public void Visit(FileFileSystemComponent component)
    {
        _builder.Append(' ', _padding);
        _builder.AppendLine(component.Name);
    }

    public void Visit(DirectoryFileSystemComponent component)
    {
        _builder.Append(' ', _padding);
        _builder.AppendLine(component.Name);

        _padding += 1;

        foreach (IFileSystemComponent child in component.Components)
        {
            child.Accept(this);
        }

        _padding -= 1;
    }
}
  • [правка] на слайде после обхода детей стояло второе _padding += 1; — отступ рос бы и у соседних папок. Исправлено на _padding -= 1;
  • Результат копится в _builder и _padding

1.24

Роли по книге

Посетитель описывает общий интерфейс для всех типов посетителей. Он объявляет набор методов, которые принимают различные классы компонентов в качестве параметров. В языках, поддерживающих перегрузку методов, эти методы могут иметь одинаковые имена, но типы их параметров должны отличаться.
Конкретные компоненты реализуют методы принятия посетителя. Цель этого метода — вызвать тот метод посещения, который соответствует типу этого компонента. Так посетитель узнает, с каким именно компонентом он работает.

А. Швец, «Погружение в паттерны проектирования», с. 397 · с. 398

Три блока if — сумма, купон, баллы

наивная реализация: сайт

public sealed class WebDiscountService : IDiscountService
{
    public DiscountResult Apply(DiscountRequestBase request)
    {
        if (request.TotalCost < 0
            || request.CustomerStatus is CustomerStatus.Banned)
        {
            return new DiscountResult.Inapplicable();
        }

        if (request is CouponDiscountRequest coupon
            && (coupon.CouponExpiresAt < DateTimeOffset.UtcNow
                || coupon.TotalCost < coupon.RequiredCost
                || (coupon.CustomerStatus is not CustomerStatus.Important
                    && coupon.CustomerOrderNumber == 1))
        {
            return new DiscountResult.Inapplicable();
        }

        if (request is BonusPointsDiscountRequest bonus
            && (bonus.PointsToSpend < 0
                || bonus.PointsToSpend > bonus.CustomerPointsBalance
                || bonus.TotalCost < 500))
        {
            return new DiscountResult.Inapplicable();
        }

        return new DiscountResult.Applied(0m);
    }
}
  • Купон на первом заказе — только важным покупателям
  • Баллы — от 500 ₽
  • Магическое число 500 (Don't 2)

public interface IDiscountLink : IDiscountService
{
    IDiscountLink AddNext(IDiscountLink link);
}

public abstract class DiscountLinkBase : IDiscountLink
{
    private IDiscountLink? _next;

    public abstract DiscountResult Apply(DiscountRequestBase request);

    public IDiscountLink AddNext(IDiscountLink link)
    {
        if (_next is null)
        {
            _next = link;
        }
        else
        {
            _next.AddNext(link);
        }

        return this;
    }

    protected DiscountResult CallNext(DiscountRequestBase request)
    {
        return _next?.Apply(request)
               ?? throw new InvalidOperationException("Chain missing terminal link");
    }
}

Последнее звено забыли — и это не видно при компиляции

три проблемы базового класса

  • В цепочке нет последнего звена. Сборка заканчивается проверкой BonusCostValidationLink: звена, которое считает скидку, нет. }

public interface ILink<TRequest, TResponse> :

Условие фильтра — через конструктор; документ — аргумент

команда над объектом

public sealed record FieldCondition(string Field, string ExpectedValue);

public sealed class FilterObjectNodeCommand : INodeCommand
{
    private readonly FieldCondition _condition;

    public FilterObjectNodeCommand(FieldCondition condition)
    {
        _condition = condition;
    }

    public NodeCommandExecutionResult Execute(JsonDocument document)
    {
        if (document is not JsonObjectDocument obj)
            return new NodeCommandExecutionResult.InvalidInput();

        return obj.Fields.Any(field => field.Name == _condition.Field && field.Value == _condition.ExpectedValue)
            ? new NodeCommandExecutionResult.Success(obj)
            : new NodeCommandExecutionResult.Filtered();
    }
}

Массив фильтруется той же командой над объектом

команда над массивом

public sealed class FilterArrayNodeCommand : INodeCommand
{
    private readonly FilterObjectNodeCommand _objectCommand;

    public FilterArrayNodeCommand(FilterObjectNodeCommand objectCommand)
    {
        _objectCommand = objectCommand;
    }

    public NodeCommandExecutionResult Execute(JsonDocument document)
    {
        if (document is not JsonArrayDocument array)
            return new NodeCommandExecutionResult.InvalidInput();

        JsonObjectDocument[] values = array.Values
            .Where(value => _objectCommand.Execute(value) is NodeCommandExecutionResult.Success)
            .ToArray();

        return new NodeCommandExecutionResult.Success(new JsonArrayDocument(values));
    }
}

История не знает ни одной конкретной команды

public sealed class CommandHistory
{
    private readonly Stack<IEditorCommand> _done = new();
    private readonly Stack<IEditorCommand> _undone = new();

    public void Run(IEditorCommand command)
    {
        command.Execute();
        _done.Push(command);
        _undone.Clear();
    }

    public void Undo()
    {
        if (_done.TryPop(out IEditorCommand? command) is false)
            return;

        command.Undo();
        _undone.Push(command);
    }

    public void Redo()
    {
        if (_undone.TryPop(out IEditorCommand? command) is false)
            return;

        command.Execute();
        _done.Push(command);
    }
}
  • Новое действие после отмены очищает стек повтора — как в любом редакторе
  • Отмена при пустой истории ничего не делает

Для C++-человека: Stack<T> — аналог std::stack. TryPop(out var x) возвращает false на пустом стеке вместо исключения — проверка и извлечение в одном вызове.

public class FileFilter : IFileFilter

        IFileSystemComponent component,
        string suffix)

        component.Accept(visitor);

        public void Visit(FileFileSystemComponent component)
        {
            _allFiles.Add(component);

4.6

IEnumerator<T> — «итератор» из структуры курса

интерфейс итератора уже есть в .NET

public interface IEnumerator<T>
{
    bool MoveNext();

    T Current { get; }

    void Reset();
}

Для C++-человека: IEnumerator<T> — как пара итераторов begin()/end() в одном объекте: MoveNext() = ++it и проверка it != end, Current = *it. До первого MoveNext итератор стоит перед первым элементом.

4.7

Итератор сам является визитором; две очереди — файлы и папки

итератор по файлам: поля

public class FileIterator : IFileSystemComponentVisitor, IEnumerator<FileFileSystemComponent>
{
    private readonly Queue<FileFileSystemComponent> _returnQueue = [];
    private readonly Queue<DirectoryFileSystemComponent> _iterateQueue = [];

    private readonly IFileSystemComponent _rootComponent;
    private FileFileSystemComponent? _current;

    public FileIterator(IFileSystemComponent component)
    {
        _rootComponent = component;
        Reset();
    }

    public FileFileSystemComponent Current
        => _current ?? throw new InvalidOperationException("No current file");

    object IEnumerator.Current => Current;
  • Использует Accept/Visit из блока 1, чтобы узнать, файл перед ним или папка, — без switch по типам
  • _returnQueue — файлы, готовые к выдаче; _iterateQueue — папки, которые ещё не раскрыты
  • [правка] object IEnumerator.Current на слайде не было: IEnumerator<T> наследует необобщённый IEnumerator, и без этого свойства код не компилируется

Для C++-человека: object IEnumerator.Current — явная реализация интерфейса: свойство видно только через ссылку типа IEnumerator, у FileIterator снаружи остаётся одно Current нужного типа.

    public OrderFeed(IOrderApi api)

Сменить состояние в обход правил нельзя

что видно снаружи

  • UpdateState, Rate и Ban ядра клиенту не видны — фасад их не открывает
  • Снаружи Submission выглядит так же, как наивная реализация
  • Проверено прогоном: активную сдачу нельзя активировать; деактивированную нельзя оценить; после активации оценка проходит, баллы и время сохраняются; завершённую нельзя оценить повторно или деактивировать; бан обнуляет баллы, время завершения остаётся; забаненную нельзя ни забанить, ни активировать

Для C++-человека: Points? у record — ссылка, которая может быть null; DateTimeOffset? — значение «или ничего», как std::optional<DateTimeOffset>. С Nullable компилятор предупредит, если обратиться к ним без проверки.

Состояние можно рассматривать как надстройку над Стратегией. Оба паттерна используют композицию, чтобы менять поведение основного объекта, делегируя работу вложенным объектам-помощникам. Однако в Стратегии эти объекты не знают друг о друге и никак не связаны. В Состоянии сами конкретные состояния могут переключать контекст.

А. Швец, «Погружение в паттерны проектирования», с. 363

Критерий оценки из лекции 7 выбирает клиент — и он не меняется. Следующее состояние выбирает текущее: ActiveSubmissionState.TryRate создаёт CompletedSubmissionState

Посредник: определение книги

Посредник — это поведенческий паттерн проектирования, который позволяет уменьшить связанность множества классов между собой, благодаря перемещению этих связей в один класс-посредник.

А. Швец, «Погружение в паттерны проектирования», с. 302

Формулировки курса для посредника нет — блок добавлен в этом году

7.1

Роли

Компоненты — это разнородные объекты, содержащие бизнес-логику программы. Каждый компонент хранит ссылку на объект посредника, но работает с ним только через абстрактный интерфейс посредников.
Посредник определяет интерфейс для обмена информацией с компонентами.

А. Швец, «Погружение в паттерны проектирования», с. 307 · с. 307

«При этом компонент-отправитель не знает, кто обработает его запрос, а компонент-получатель не знает, кто его прислал» (с. 308)

7.3

Датчик сообщает, что случилось, а не что делать

события и датчики

public sealed record Room(string Name);

public abstract record HomeEvent
{
    private HomeEvent() { }

    public sealed record MotionDetected(Room Room) : HomeEvent;

    public sealed record DoorOpened : HomeEvent;
}

public interface IHomeMediator
{
    void Notify(HomeEvent homeEvent);
}

public sealed class MotionSensor
{
    private readonly IHomeMediator _mediator;
    private readonly Room _room;

    public MotionSensor(IHomeMediator mediator, Room room)
    {
        _mediator = mediator;
        _room = room;
    }

    public void Detect()
        => _mediator.Notify(new HomeEvent.MotionDetected(_room));
}
  • Событие — иерархия record с данными, как результаты в остальных примерах лекции
  • Датчик знает только интерфейс посредника
  • Датчик двери устроен так же — метод Open отправляет DoorOpened
7.4

Посредник знает устройства — но не датчики

хаб: правила в одном месте

public sealed class SmartHomeHub : IHomeMediator
{
    private const int NightStartsAt = 22;
    private const int NightEndsAt = 7;

    private readonly ILighting _lighting;
    private readonly IAlarm _alarm;
    private readonly TimeProvider _timeProvider;
    private bool _isArmed;

    public SmartHomeHub(ILighting lighting, IAlarm alarm, TimeProvider timeProvider)
    {
        _lighting = lighting;
        _alarm = alarm;
        _timeProvider = timeProvider;
    }

    public void Arm()
        => _isArmed = true;

    public void Disarm()
        => _isArmed = false;
  • Зависимости через конструктор (Do 13)
  • Время — через TimeProvider, как в цепочке скидок из блока 2
  • Границы ночи — именованные константы (Don't 2)
7.5

Switch по типу события с условиями when

хаб: обработка событий

продолжение

    public void Notify(HomeEvent homeEvent)
    {
        switch (homeEvent)
        {
            case HomeEvent.MotionDetected motion when IsNight():
                _lighting.TurnOn(motion.Room);
                break;

            case HomeEvent.DoorOpened when _isArmed:
                _alarm.Raise();
                break;
        }
    }

    private bool IsNight()
    {
        int hour = _timeProvider.GetLocalNow().Hour;
        return hour >= NightStartsAt || hour < NightEndsAt;
    }
}
  • Все правила взаимодействия — в одном классе. Новое правило «при тревоге включить свет везде» — правка только хаба; датчики и устройства не меняются
  • Циклической зависимости нет, всё создаётся через конструкторы
  • Проверено прогоном: ночью движение в коридоре включает свет, днём — нет; дверь до включения охраны не поднимает тревогу, после — поднимает

Для C++-человека: case X x when условие: — ветка срабатывает, только если объект нужного типа и выполнено условие. Событие, не попавшее ни в одну ветку, просто игнорируется — здесь это осознанное поведение.

7.6

Строковые события — против типизированных

книга и курс: события и связи

Книга Швеца
  • В псевдокоде событие — строка: notify(sender: Component, event: string), сравнения вида event == "click"
  • О конкретном посреднике: «Этот объект создаёт и хранит ссылки на компоненты системы» (с. 308)

с. 308–310

Курс
  • Событие — тип, а не строка: иерархия record с данными. Опечатку в имени события ловит компилятор
  • Посредник не создаёт компоненты — получает зависимости через конструктор (Do 13)
  • Отправители знают посредника, посредник — получателей; двусторонних ссылок нет, поэтому не нужен сеттер «подключить посредника потом»

Правило для ЛР4: событие — тип, не строка; посредник получает зависимости через конструктор

посредник, наблюдатель, фасад

Посредник и наблюдатель

Четыре способа связать отправителя и получателя

Цепочка обязанностей, Команда, Посредник и Наблюдатель показывают различные способы работы отправителей запросов с их получателями:
  • Цепочка обязанностей передаёт запрос последовательно через цепочку потенциальных получателей, ожидая, что какой-то из них обработает запрос.
  • Команда устанавливает косвенную одностороннюю связь от отправителей к получателям.
  • Посредник убирает прямую связь между отправителями и получателями, заставляя их общаться опосредованно, через себя.
  • Наблюдатель передаёт запрос одновременно всем заинтересованным получателям, но позволяет им динамически подписывать или отписываться от таких оповещений.

А. Швец, «Погружение в паттерны проектирования», с. 264–265
