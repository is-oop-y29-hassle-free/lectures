1.1

Единственная ответственность

Принцип единственной ответственности направлен на локализацию логики, описываемой типом, минимизации области его ответственности в моделируемой системе.
Основным правилом, используемым для определения соблюдения данного принципа, является наличие у типа единственной причины для изменения.

1.2

Чем SRP не является

Единственная ответственность ≠ одно поле или один метод.

  • Тип может иметь набор данных и поведений
  • Они должны быть логически согласованы с точки зрения бизнес-процессов
  • Больше одной логической группы — декомпозировать

Единственная причина для изменения

Под понятием “единственной причины для изменения” подразумевается, что модификацией типа должны служить изменения только одного бизнес требования, никак не нескольких.

Когда OCP не нужен

Именно этим разработчик и отличается от программиста, разработчик должен уметь анализировать требования к системе, которые получает от бизнеса.

2.4

Нарушение: новая операция — правка Evaluate

Чтобы добавить умножение, придётся открыть и enum, и класс.

public enum BinaryOperation
{
    Summation,
    Subtraction,
}
 
public class BinaryOperand
{
    private readonly int _left;
    private readonly int _right;
 
    // ...
 
    public int Evaluate(BinaryOperation operation)
    {
        return operation switch 
        {
            BinaryOperation.Summation => _left + _right,
            BinaryOperation.Subtraction => _left - _right,
        };
    }
}
На что смотреть
  • Здесь сломать трудно — логика простая
  • На сложной логике — все проблемы SRP
Для C++-человека: enum — как enum class, со своей областью имён; operation switch { … => … } — switch-выражение, возвращает значение, без case/break.
SOLID
2.5

Исправление: операция — это тип

Новая операция — новый класс; существующий код и тесты не меняются.

public interface IBinaryOperation
{
    int Evaluate(int left, int right);
}
 
public class Summation : IBinaryOperation
{
    public int Evaluate(int left, int right)
            => left + right;
}
 
public class Subtraction : IBinaryOperation
{
    public int Evaluate(int left, int right)
            => left - right;
}
public sealed class BinaryOperand
{
    private readonly int _left;
    private readonly int _right;
 
    // ...
 
    public int Evaluate(IBinaryOperation operation)
        => operation.Evaluate(_left, _right);
}
BinaryOperand — sealed: закрыт буквально
Расширение — через реализации IBinaryOperation
Добавляются только новые тесты
Для C++-человека: sealed — как final на классе.

3.3

Формулировка

есть определение через теорию категорий; скажем по-простому

Суть принципа подстановки Лисков заключается в том, что реализация дочернего типа, не должна нарушать инвариант своего родителя, соответственно, все дочерние реализации, должны быть применимы везде, где ожидается родительская.
Определить это достаточно просто, если результат операции, переопределённой дочерним типом, разнится с тем, что явно ожидается от результата вызова реализации родительского типа, то данный принцип не соблюдается.

3.4

Шаг 1. Пингвин умирает при попытке взлететь

У Bird результат FlyTo — полёт, у Penguin — смерть. Результат разнится — LSP нарушен.

public class Creature
{
    public void Die()
    {
        Console.WriteLine("I am dead now");
    }
}
 
public class Bird : Creature
{
    public virtual void FlyTo(Coordinate coordinate)
    {
        Console.WriteLine("I am flying");
    }
}
 
public class Penguin : Bird
{
    public override void FlyTo(Coordinate coordinate)
    {
        Die();
    }
}
На что смотреть
  • Пингвины не летают — и разработчик не придумал ничего лучше
  • Мы не хотим пингвиньих смертей

Шаг 3. Проверка типов — не выход

Каждый новый летающий вид — новый if. Это нарушение OCP, и пингвин всё ещё умирает.

public class Bat : Creature
{
    public void FlyTo(Coordinate coordinate)
    {
        Console.WriteLine("I bat and am flying");
    }
}
 
void StartMigration(IEnumerable<Creature> creatures, Coordinate coordinate)
{
    foreach (var creature in creatures)
    {
        if (creature is Bird bird)
        {
            bird.FlyTo(coordinate);
        }
 
        if (creature is Bat bat)
        {
            bat.FlyTo(coordinate);
        }
    }
}
 
var creatures = new Creature[] { new Penguin(), new Bat() };
 
StartMigration(creatures, new Coordinate(420, 69));
Не все птицы летают
Не все, кто летает, — птицы
Don't 7: минимизировать down casting
Для C++-человека: creature is Bird bird — проверка типа с приведением, как dynamic_cast внутри if.

3.7

Шаг 4. Абстракция летающего существа

У пингвина больше нет FlyTo — летать его никто не попросит.

public interface ICreature
{
    void Die();
}
 
public interface IFlyingCreature : ICreature
{
    void FlyTo(Coordinate coordinate);
}
 
public class CreatureBase : ICreature
{
    public void Die()
    {
        Console.WriteLine("I am dead now");
    }
}
 
public class Bird : CreatureBase { }
public class Colibri : Bird, IFlyingCreature
{
    public void FlyTo(Coordinate coordinate)
    {
        Console.WriteLine("I am colibri and I'm flying");
    }
}
 
public class Penguin : Bird { }
 
public class Bat : CreatureBase, IFlyingCreature
{
    public void FlyTo(Coordinate coordinate)
    {
        Console.WriteLine("I am bat and I'm flying");
    }
}
Наследование интерфейсов связывает абстракции — в общем случае не лучшая практика
Здесь приемлемо: между ними is a
Для C++-человека: IFlyingCreature : ICreature — интерфейс наследует интерфейс; Colibri : Bird, IFlyingCreature — один базовый класс плюс интерфейсы через запятую.

Соблюдение кодом

Зависимость приходит через конструктор, а не создаётся внутри.

// Соблюдение: сервис зависит от абстракции, реализацию передают снаружи
public interface ILogger
{
    void Write(string message);
}
 
public class FileLogger : ILogger
{
    public FileLogger(string path) { _path = path; }
    private readonly string _path;
    public void Write(string message) { /* ... */ }
}
 
public class OrderService
{
    public OrderService(ILogger logger) { _logger = logger; }
    private readonly ILogger _logger;
 
    public void Place(Order order)
    {
        _logger.Write($"Placing order {order.Id}");
        // ...
    }
}

  • OrderService не знает, что такое файл
