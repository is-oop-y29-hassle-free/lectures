# Бриф для Claude Design: презентация «Лекция 2. SOLID»

## Общие требования

- **Формат:** 16:9, 49 слайдов, язык — русский. Лекция на 90 минут для студентов 2 курса; C# они знают на уровне первой лекции и начала ЛР1.
- **Только светлая тема.** Аудитория светлая, проекторы старые, картинку просвечивает солнце. Фон — белый или почти белый (без серых заливок на весь слайд), текст — почти чёрный. Никаких тёмных слайдов, включая титул и блоки кода. Тонкий светло-серый текст запрещён — минимальный контраст как у тёмно-серого на белом. Кегль основного текста не меньше 20 pt, сносок — не меньше 16 pt.
- **Цвета:** один акцентный (насыщенный тёмно-синий или тёмно-зелёный — для определений и «правильного» кода) и один предупреждающий (тёмно-красный — для нарушений и штрафов). Оба должны читаться при засветке: тёмные и плотные, не пастельные. Нейтральные серые — только для рамок и фона кода.
- **F-pattern на каждом слайде.** Взгляд идёт: заголовок → первая строка под ним → вниз по левому краю. Поэтому:
  - Заголовок — один тезис, не название темы («Пингвин умирает при компиляции без ошибок», а не «LSP, шаг 2»).
  - Под заголовком — **одна ключевая строка**: самое важное, что нужно унести с этого слайда.
  - Дальше — короткая колонка слева: не больше трёх пунктов, каждый в одну строку.
  - Всё крупное (код, схема, таблица) — справа от колонки или под ключевой строкой; не больше одного крупного объекта на слайд.
  - Никаких блоков текста абзацами. Если содержание не помещается — это два слайда.
- **Четыре шаблона слайдов, использовать только их:**
  - **A — Определение.** Заголовок; под ним акцентная плашка: рамка в акцентном цвете, слева вертикальная полоса, кегль крупнее основного, текст **дословно, менять нельзя** (включая пунктуацию и обороты вроде «по факту»). Помечены ниже как **[ОПРЕДЕЛЕНИЕ]**. На слайде — только плашка и, если указано, одна строка-подзаголовок. Если на слайде две плашки — они одинаковой ширины, одна под другой.
  - **B — Код.** Заголовок; ключевая строка; блок кода занимает левые ~60% ширины (светло-серый фон, тёмный моноширинный текст, подсветка синтаксиса насыщенными цветами, без нумерации строк); справа узкая колонка: до трёх пунктов «на что смотреть». Внизу справа — сноска **«Для C++-человека»** в отличающемся стиле (курсив, иконка стрелки C++ → C#). Код приводится дословно, не переформатировать. Строки для подсветки указаны; подсвечивать фоном — акцентным для «правильного», предупреждающим для «нарушения».
  - **C — Тезисы.** Заголовок; ключевая строка; до трёх пунктов слева; справа — иконка, мини-схема или пусто.
  - **D — Схема.** Заголовок; ключевая строка; схема по центру/справа; слева — не больше двух подписей.
- **Единый ритм принципов.** Каждый из пяти блоков SOLID начинается со слайда-разделителя: крупная буква в акцентном цвете, полное название принципа, позиция в аббревиатуре (например, «S · O · L · I · D» с подсвеченной буквой). Этот же элемент в уменьшенном виде — в углу всех слайдов блока, как индикатор.
- **Иконки:** минимальный набор: щит = проверка/защита, предупреждающий треугольник = нарушение, галочка в круге = исправление, стрелка C++ → C# = сноска.
- **Логотипы, стоковые фото, сгенерированные портреты не использовать.** На слайде про Барбару Лисков — место под реальную фотографию, которую вставит лектор (Wikimedia Commons, с подписью источника); ничего не генерировать.
- Код-термины в обычном тексте (`ReportGenerator`, `switch`, `IFlyingCreature`) — моноширинным.
- Нижний колонтитул: номер блока и слайда, например «3.4».

Тайминг блоков: 0 — 7 мин · S — 18 · O — 18 · L — 18 · I — 8 · D — 13 · Итоги — 8.

## Блок S. Single responsibility (слайды 6–16)

### Слайд 6 — Разделитель «S»

### Слайд 7 — Единственная ответственность (A, две плашки)
- **[ОПРЕДЕЛЕНИЕ]:** Принцип единственной ответственности направлен на локализацию логики, описываемой типом, минимизации области его ответственности в моделируемой системе.
- **[ОПРЕДЕЛЕНИЕ]:** Основным правилом, используемым для определения соблюдения данного принципа, является наличие у типа единственной причины для изменения.

### Слайд 8 — Чем SRP не является (C)
- **Ключевая строка:** единственная ответственность ≠ одно поле или один метод.
- Тип может иметь набор данных и поведений · Они должны быть логически согласованы с точки зрения бизнес-процессов · Больше одной логической группы — декомпозировать.

### Слайд 9 — Единственная причина для изменения (A)
- **[ОПРЕДЕЛЕНИЕ]:** Под понятием “единственной причины для изменения” подразумевается, что модификацией типа должны служить изменения только одного бизнес требования, никак не нескольких.

### Слайд 10 — Требование и правило (A + мини-схема справа)
- **[ОПРЕДЕЛЕНИЕ]:** бизнес требования, это более комплексная сущность, например, бизнес требованием является то, что результат выполнения какой-либо операции должен быть выгружен в Excel таблицу, бизнес правила же, скорее являются составными частями бизнес требований, например, бизнес правилами являются условия, что отчёт должен содержать шапку, а колонки иметь определённые заголовки, порядок и ширину.
- Справа мини-схема: большой прямоугольник «Требование: выгрузка в Excel», внутри три маленьких «шапка», «заголовки колонок», «ширина». Подпись: «правила меняются — причина та же».

### Слайд 11 — Нарушение: две причины для изменения (B)
- **Ключевая строка:** `ReportGenerator` отвечает за Excel и за PDF — два требования.
- Код (подсветить оба имени методов предупреждающим):
```csharp
public record OperationResult(...);

public class ReportGenerator
{
    public void GenerateExcelReport(OperationResult result)
    {
        ...
    }

    public void GeneratePdfReport(OperationResult result)
    {
        ...
    }
}
```
- Справа: «Заказчик поменял ширину колонок в Excel» · «Какой файл открываете?» · «Тесты PDF перезапускаете?»
- Сноска: `record` — тип, который автоматически получает конструктор, свойства, сравнение по значению и `ToString`; `(...)` — поля здесь намеренно опущены.

### Слайд 12 — Исправление: абстракция и два типа (B)
- **Ключевая строка:** одна абстракция генератора, две реализации — по одной причине для изменения у каждой.
- Код (подсветить `IReportGenerator` акцентным):
```csharp
public record OperationResult(...);

public interface IReportGenerator
{
    void GenerateReport(OperationResult result);
}

public class ExcelReportGenerator : IReportGenerator
{
    public void GenerateReport(OperationResult result)
    {
        ...
    }
}

public class PdfReportGenerator : IReportGenerator
{
    public void GenerateReport(OperationResult result)
    {
        ...
    }
}
```
- Справа: «Меняется Excel — открываем только `ExcelReportGenerator`» · «PDF не тронут, его тесты не запускаем».

### Слайд 13 — Чем подкупает нарушение (C)
- **Ключевая строка:** правила не появляются на пустом месте — сначала признаем, что в первом варианте удобно.
- **Простота** — не нужно абстракций; в месте использования `if` по строке и вызов метода · **Переиспользование** — форматирование чисел, разметка, логгирование общие для обоих форматов.

### Слайд 14 — Ловушка первая: связанность требований (C)
- **Ключевая строка:** объединяя реализации, объединяем и их зависимости.
- Лёгкое: лишние `using`, IntelliSense подсказывает не то · Тяжёлое: одной реализации нужна одна зависимость, другой — другая · Тесты: чтобы проверить Excel, инициализируем всё, что нужно PDF, — заглушки, и лишняя зависимость не даст ошибку компиляции.

### Слайд 15 — Ловушка вторая: кастомизация (C)
- **Ключевая строка:** общий код — общая точка отказа.
- Изменили под новые требования Excel — сломали PDF · Повезёт, если у PDF тесты на все кейсы · Проверяют то, что меняли, — решение уезжает в продакшен.

### Слайд 16 — Кумулятивный эффект и «как найти у себя» (C)
- **Ключевая строка:** по отдельности не страшно; на растущей кодовой базе — коллективная борьба с написанным кодом.
- Слева три вопроса: «Сколько разных требований заставят открыть этот файл?» · «Есть ли методы, не трогающие одни и те же поля?» · «Назову ли класс одним существительным без „и“, Manager, Helper, Utils?»
- Внизу строка со ссылкой на документ: **Do 12** — разделять бизнес-логику и UI, логику и валидацию · **Don't 3** — не работать с вводом-выводом в бизнес-логике. Подпись: «самое частое нарушение в ЛР1 — `Console.WriteLine` внутри класса предметной области».

## Блок O. Open-closed (слайды 17–23)

### Слайд 17 — Разделитель «O»
- Подпись под буквой: «самый сложный для понимания принцип SOLID».

### Слайд 18 — Открыт для расширения, закрыт для изменения (A)
- **[ОПРЕДЕЛЕНИЕ]:** Тип должен быть открыт для расширения и закрыт для изменения.
- Строка-подзаголовок под плашкой, курсивом: «Как расширить логику типа, не изменяя его?» — вопрос в зал.

### Слайд 19 — Ответ (A)
- **[ОПРЕДЕЛЕНИЕ]:** На самом деле, ответ достаточно прост – абстракции и полиморфизм.

### Слайд 20 — Когда OCP не нужен (A + три пункта под плашкой)
- **[ОПРЕДЕЛЕНИЕ]:** Именно этим разработчик и отличается от программиста, разработчик должен уметь анализировать требования к системе, которые получает от бизнеса.
- Под плашкой три пункта слева: «Иногда тип — это просто тип» · «Абстракции окупаются, если требования нестабильны и другое поведение понадобится в обозримом будущем» · «Рефакторинг всегда несёт риск сломать и тянет за собой тесты».
- Строка внизу: «YAGNI (Do 21) — „не делай заранее“. OCP — „а если делать, то так“».

### Слайд 21 — Нарушение: новая операция — правка `Evaluate` (B)
- **Ключевая строка:** чтобы добавить умножение, придётся открыть и `enum`, и класс.
- Код (подсветить `switch` предупреждающим):
```csharp
public enum BinaryOperation
{
    Summation,
    Subtraction,
}

public class BinaryOperand
{
    private readonly int _left;
    private readonly int _right;

    // ...

    public int Evaluate(BinaryOperation operation)
    {
        return operation switch 
        {
            BinaryOperation.Summation => _left + _right,
            BinaryOperation.Subtraction => _left - _right,
        };
    }
}
```
- Справа: «Здесь сломать трудно — логика простая» · «На сложной логике — все проблемы SRP».
- Сноска: `enum` — как `enum class`, со своей областью имён; `operation switch { … => … }` — `switch`-выражение, возвращает значение, без `case`/`break`.

### Слайд 22 — Исправление: операция — это тип (B)
- **Ключевая строка:** новая операция — новый класс; существующий код и тесты не меняются.
- Код (подсветить `sealed` и `IBinaryOperation` акцентным):
```csharp
public interface IBinaryOperation
{
    int Evaluate(int left, int right);
}

public class Summation : IBinaryOperation
{
    public int Evaluate(int left, int right)
            => left + right;
}

public class Subtraction : IBinaryOperation
{
    public int Evaluate(int left, int right)
            => left - right;
}

public sealed class BinaryOperand
{
    private readonly int _left;
    private readonly int _right;

    // ...

    public int Evaluate(IBinaryOperation operation)
        => operation.Evaluate(_left, _right);
}
```
- Справа: «`BinaryOperand` — `sealed`: закрыт буквально» · «Расширение — через реализации `IBinaryOperation`» · «Добавляются только новые тесты».
- Сноска: `sealed` — как `final` на классе.

### Слайд 23 — Тест на OCP: вы разработчик библиотеки (D)
- **Ключевая строка:** ваш код поставляется как dll — исходников у потребителя нет.
- Схема: коробка «ваша dll» с замком; слева пользователь со стрелкой «хочу добавить умножение». Две дорожки: к варианту с `enum` — крестик, «нужны исходники → OCP нарушен»; к варианту с `IBinaryOperation` — галочка, «добавил свой класс → OCP соблюдён».
- Слева два вопроса «как найти у себя»: «Есть ли `switch`/`if` по типу или `enum`, куда придётся добавлять ветку?» · «Стабильна ли логика? Если да — не трогать».

### Слайд 25 — Наследование — сильная связь (C)
- **Ключевая строка:** иерархию, вросшую в кодовую базу, трудно разорвать.

- Справа — рамка-плейсхолдер под фотографию с подписью «фото: Wikimedia Commons». Портрет не генерировать.

### Слайд 27 — Формулировка (A, две плашки)
- Подзаголовок курсивом: «есть определение через теорию категорий; скажем по-простому».
- **[ОПРЕДЕЛЕНИЕ]:** Суть принципа подстановки Лисков заключается в том, что реализация дочернего типа, не должна нарушать инвариант своего родителя, соответственно, все дочерние реализации, должны быть применимы везде, где ожидается родительская.
- **[ОПРЕДЕЛЕНИЕ]:** Определить это достаточно просто, если результат операции, переопределённой дочерним типом, разнится с тем, что явно ожидается от результата вызова реализации родительского типа, то данный принцип не соблюдается.

### Слайд 28 — Шаг 1. Пингвин умирает при попытке взлететь (B)
- **Ключевая строка:** у `Bird` результат `FlyTo` — полёт, у `Penguin` — смерть. Результат разнится — LSP нарушен.
- Код (подсветить `Die();` внутри `Penguin` предупреждающим):
```csharp
public class Creature
{
    public void Die()
    {
        Console.WriteLine("I am dead now");
    }
}

public class Bird : Creature
{
    public virtual void FlyTo(Coordinate coordinate)
    {
        Console.WriteLine("I am flying");
    }
}

public class Penguin : Bird
{
    public override void FlyTo(Coordinate coordinate)
    {
        Die();
    }
}
```
- Справа: «Пингвины не летают — и разработчик не придумал ничего лучше» · «Мы не хотим пингвиньих смертей».

### Слайд 29 — Шаг 2. Компилятор с радостью пропустит (B)
- **Ключевая строка:** пингвин — птица; компилятор прав; миграция убивает пингвина.
- Код (подсветить `new Penguin()` предупреждающим):
```csharp
void StartMigration(IEnumerable<Bird> birds, Coordinate coordinate)
{
    foreach (var bird in birds)
    {
        bird.FlyTo(coordinate);
    }
}

var birds = new[] { new Penguin() };

StartMigration(birds, new Coordinate(420, 69));
```
- Справа: «Это и есть лишнее пространство для ошибок».
- Сноска: `IEnumerable<T>` — «то, по чему можно пройти `foreach`»; `new[] { … }` — массив с выводом типа.

### Слайд 30 — Шаг 3. Проверка типов — не выход (B)
- **Ключевая строка:** каждый новый летающий вид — новый `if`. Это нарушение OCP, и пингвин всё ещё умирает.
- Код (подсветить обе строки `if (creature is …)` предупреждающим):
```csharp
public class Bat : Creature
{
    public void FlyTo(Coordinate coordinate)
    {
        Console.WriteLine("I bat and am flying");
    }
}

void StartMigration(IEnumerable<Creature> creatures, Coordinate coordinate)
{
    foreach (var creature in creatures)
    {
        if (creature is Bird bird)
        {
            bird.FlyTo(coordinate);
        }

        if (creature is Bat bat)
        {
            bat.FlyTo(coordinate);
        }
    }
}

var creatures = new Creature[] { new Penguin(), new Bat() };

StartMigration(creatures, new Coordinate(420, 69));
```
- Справа: «Не все птицы летают» · «Не все, кто летает, — птицы» · «Don't 7: минимизировать down casting».
- Сноска: `creature is Bird bird` — проверка типа с приведением, как `dynamic_cast` внутри `if`.

### Слайд 31 — Шаг 4. Абстракция летающего существа (B)
- **Ключевая строка:** у пингвина больше нет `FlyTo` — летать его никто не попросит.
- Код (подсветить `IFlyingCreature : ICreature` акцентным):
```csharp
public interface ICreature
{
    void Die();
}

public interface IFlyingCreature : ICreature
{
    void FlyTo(Coordinate coordinate);
}

public class CreatureBase : ICreature
{
    public void Die()
    {
        Console.WriteLine("I am dead now");
    }
}

public class Bird : CreatureBase { }

public class Colibri : Bird, IFlyingCreature
{
    public void FlyTo(Coordinate coordinate)
    {
        Console.WriteLine("I am colibri and I'm flying");
    }
}

public class Penguin : Bird { }

public class Bat : CreatureBase, IFlyingCreature
{
    public void FlyTo(Coordinate coordinate)
    {
        Console.WriteLine("I am bat and I'm flying");
    }
}
```
- Справа: «Наследование интерфейсов связывает абстракции — в общем случае не лучшая практика» · «Здесь приемлемо: между ними *is a*».
- Сноска: `IFlyingCreature : ICreature` — интерфейс наследует интерфейс; `Colibri : Bird, IFlyingCreature` — один базовый класс плюс интерфейсы через запятую.

### Слайд 32 — Миграция без случайных смертей (B)
- **Ключевая строка:** пингвина в этот массив не положить — компилятор не даст. Ошибка ушла с рантайма на компиляцию.
- Код:
```csharp
void StartMigration(IEnumerable<IFlyingCreature> creatures, Coordinate coordinate)
{
    foreach (var creature in creatures)
    {
        if (Random.Shared.NextDouble() < 0.8)

        else

var creatures = new IFlyingCreature[] { new Colibri(), new Bat() };

```

- Сноска: `Random.Shared` — готовый общий генератор, без `srand`.

### Слайд 33 — Как найти у себя (C)
- **Ключевая строка:** Don't 11 — единственный пункт Do/Don't, который прямо ссылается на LSP.
- «Есть ли `override`, который бросает исключение, ничего не делает или делает „не то“?» · «Есть ли `is`/`as` на конкретный наследник в коде про родителя?» · «Подставлю любого наследника вместо родителя — получу *ожидаемый* результат?»

## Блок D. Dependency inversion (слайды 39–45)

### Слайд 39 — Разделитель «D»

### Слайд 40 — Формулировка (A)
- **[ОПРЕДЕЛЕНИЕ]:** Принцип инверсии зависимостей направлен на снижение связанности между модулями. Основная его идея заключается в том, что одни реализации не должны зависеть от других.

### Слайд 41 — Уровни доменной значимости (D)
- **Ключевая строка:** бизнес-логика не должна зависеть от реализации логгирования.
- Схема: два уровня, верхний «Бизнес-логика: `OrderService`», нижний «Инфраструктура: логгер, файлы, консоль». Подпись у нижнего: «меньший уровень доменной значимости — чаще меняется: сменится хранилище логов, появится несколько точек записи».

### Слайд 42 — Откуда слово «инверсия» (D, две схемы рядом — генерировать по описанию)
- **Ключевая строка:** стрелка со стороны инфраструктуры развернулась.
- **Левая схема «Нарушение»:** прямоугольник `OrderService` (подпись «бизнес-логика»), сплошная стрелка вниз к прямоугольнику `FileLogger` (подпись «инфраструктура»). Стрелка предупреждающего цвета.
- **Правая схема «Соблюдение»:** `OrderService` сверху, сплошная стрелка вниз к прямоугольнику с пунктирной рамкой `«interface» ILogger`; ниже `FileLogger`, от него пунктирная стрелка **вверх** к `ILogger` (реализация). Стрелка вверх — акцентным цветом, выделена как «инвертированная».
- Слева одна подпись: «Обе стороны зависят от абстракции».

### Слайд 43 — Нарушение кодом (B)
- **Ключевая строка:** сервис сам создаёт конкретный логгер — и знает, что такое файл.
- Код (подсветить `new FileLogger(...)` предупреждающим):
```csharp
// Нарушение: сервис создаёт и использует конкретный логгер
public class OrderService
{
    private readonly FileLogger _logger = new FileLogger("orders.log");

    public void Place(Order order)
    {
        _logger.Write($"Placing order {order.Id}");
        // ...
    }
}
```

### Слайд 44 — Соблюдение кодом (B)
- **Ключевая строка:** зависимость приходит через конструктор, а не создаётся внутри.
- Код (подсветить `OrderService(ILogger logger)` акцентным):
```csharp
// Соблюдение: сервис зависит от абстракции, реализацию передают снаружи
public interface ILogger
{
    void Write(string message);
}

public class FileLogger : ILogger
{
    public FileLogger(string path) { _path = path; }
    private readonly string _path;
    public void Write(string message) { /* ... */ }
}

public class OrderService
{
    public OrderService(ILogger logger) { _logger = logger; }
    private readonly ILogger _logger;

    public void Place(Order order)
    {
        _logger.Write($"Placing order {order.Id}");
        // ...
    }
}
```
- Справа: «`OrderService` не знает, что такое файл» · «Кто создаёт `FileLogger` — вопрос ЛР5» · «Do 13: зависимости — аргументами».

### Слайд 45 — Негативные эффекты и «как найти у себя» (C)
- **Ключевая строка:** без абстракции нет настоящего модульного тестирования — заглушку не подставить.
- Слева: **Замена реализации** — менять и зависимого · **Чужой код** — тип из библиотеки не расширить · **Тесты** — проверяем модуль вместе со всеми его зависимостями.
- Строка внизу: «У себя: есть ли `new` конкретного типа внутри бизнес-логики — логгер, файл, консоль, `Random`, часы? Смогу ли протестировать, не создавая файлы?» · «Do 19: абстракции вместо конкретных коллекций — то же на уровне параметров».

## Итоги (слайды 46–49)

### Слайд 46 — SOLID одним экраном (D, таблица 5 строк × 3 колонки)
- **Ключевая строка:** буква — одна фраза — как выглядит нарушение в коде.

| | Принцип | Нарушение в коде |
|--|---------|------------------|
| **S** | одна причина для изменения | класс с методами про два разных требования |
| **O** | открыт для расширения, закрыт для изменения | `switch` по `enum`, растущий с каждым требованием |
| **L** | наследник применим везде, где ожидается родитель | `override`, который «делает не то» |
| **I** | маленькие специализированные абстракции | интерфейс с методами-пустышками в реализациях |
| **D** | зависеть от абстракций, а не от реализаций | `new FileLogger()` внутри сервиса |

### Слайд 47 — Как принципы связаны (D)
- **Ключевая строка:** не пять правил, а один подход: изменения локализуются, зависимости идут к абстракциям.
- Схема: пять кружков S · O · L · I · D по дуге, стрелки с подписями: I → S «SRP для абстракций»; L → O «`is`-проверки чинятся абстракцией»; O ↔ D «оба — зависеть от интерфейса».

### Слайд 48 — Чек-лист перед PR (C, пять строк)
- **Ключевая строка:** на защите ЛР1 и ЛР2 спросят именно это.
- S — сколько требований заставят открыть файл? · O — есть ли `switch`, куда придётся добавлять ветку? · L — подставлю наследника — получу ожидаемое? · I — нужны ли потребителю все методы интерфейса? · D — есть ли `new` инфраструктуры внутри логики?
- Строка внизу в предупреждающем цвете: «Проверять код у агента — нарушение силлабуса. Этот чек-лист — то, чем вы проверяете себя сами».
