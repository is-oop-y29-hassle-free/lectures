# Бриф для Claude Design: презентация «Лекция 5. Порождающие паттерны»

## Общие требования

- **Формат:** 16:9, 111 слайдов, язык — русский. Лекция на 90 минут для студентов 2 курса дисциплины «ООП и проектирование». Позади лекции по основам ООП, SOLID, GRASP и проектированию; впереди ЛР3 — порождающие паттерны. Основной референс студентов — книга А. Швеца «Погружение в паттерны проектирования».
- **Только светлая тема.** Аудитория светлая, проекторы старые, картинку просвечивает солнце. Фон — белый или почти белый (без серых заливок на весь слайд), текст — почти чёрный. Никаких тёмных слайдов, включая титул, разделители и блоки кода. Тонкий светло-серый текст запрещён — минимальный контраст как у тёмно-серого на белом. Кегль основного текста не меньше 20 pt, сносок и источников — не меньше 16 pt, кода — не меньше 16 pt.
- **Цвета:** один акцентный (насыщенный тёмно-синий или тёмно-зелёный — для определений, «правильного» кода, позиции курса) и один предупреждающий (тёмно-красный — для антипримеров, «не компилируется», «так не делаем»). Оба читаются при засветке: тёмные и плотные, не пастельные. Нейтральные серые — только для рамок и фона кода.
- **F-pattern на каждом слайде.** Взгляд идёт: заголовок → первая строка под ним → вниз по левому краю. Поэтому:
  - Заголовок — один тезис, не название темы («Строитель хранит аргументы, а не объект», а не «Строитель. Реализация»).
  - Под заголовком — **одна ключевая строка**: самое важное, что нужно унести с этого слайда.
  - Дальше — короткая колонка слева: не больше трёх пунктов, каждый в одну строку.
  - Всё крупное (код, схема, таблица) — справа от колонки или под ключевой строкой; не больше одного крупного объекта на слайд.
  - Никаких абзацев. Не помещается — значит, это два слайда. Сокращать содержание не нужно: лучше больше слайдов, чем плотнее.
- **Шесть шаблонов слайдов, использовать только их:**
  - **A — Определение.** Заголовок; под ним акцентная плашка: рамка в акцентном цвете, слева вертикальная полоса, кегль крупнее основного; текст **дословно, менять нельзя** (включая пунктуацию и опечатки — их решит лектор). Под плашкой мелким текстом — строка источника. Два вида источника, визуально различимые:
    - **из книги** — маленькая иконка книги + «А. Швец, «Погружение в паттерны проектирования», с. N»;
    - **формулировка курса** — без иконки книги, подпись «формулировка курса».
    Помечены ниже как **[ОПРЕДЕЛЕНИЕ · книга, с. N]** или **[ОПРЕДЕЛЕНИЕ · курс]**. На слайде — только плашка(и), источник и, если указано, одна строка-подзаголовок или маленький код под плашкой.
  - **B — Код.** Заголовок; ключевая строка; блок кода занимает левые ~60% ширины (светло-серый фон, тёмный моноширинный текст, подсветка синтаксиса насыщенными цветами, без нумерации строк); справа узкая колонка: до трёх пунктов «на что смотреть». Внизу справа — сноска **«Для C++-человека»**, если указана, в отличающемся стиле (курсив, иконка стрелки C++ → C#). Код приводится **дословно**, не переформатировать и не сокращать, многоточия `...` — часть кода. Строки для подсветки указаны: фоном акцентного цвета — «правильное», предупреждающего — «нарушение / не компилируется». Слайд с антипримером — тонкая предупреждающая рамка по краю. Если код разрезан на два слайда — второй начинается с пометки «продолжение» мелким текстом над кодом.
  - **C — Тезисы.** Заголовок; ключевая строка; до трёх пунктов слева; справа — иконка, мини-схема или пусто.
  - **D — Схема / таблица.** Заголовок; ключевая строка; схема или таблица по центру/справа; слева — не больше двух подписей. Таблицы — не больше 6 строк.
  - **E — Дискуссия.** Только крупный вопрос (кегль как у заголовка), слева иконка двух реплик, внизу мелко — подсказка. Ответа на слайде нет.
  - **F — Книга и курс.** Новый шаблон этой лекции: студенты читают книгу Швеца, и в нескольких местах курс решает иначе. Две равные колонки: слева «Книга Швеца» — нейтральная рамка, иконка книги, номер страницы; справа «Курс» — акцентная рамка. Внизу на всю ширину — строка «Правило для ЛР3» акцентным цветом. Колонку книги **не** окрашивать предупреждающим цветом — это не ошибка книги, а другое решение.
- **Сквозной индикатор — пять порождающих паттернов** в ряд: Фабричный метод · Фабрика · Строитель · Прототип · Одиночка. На разделителе каждого блока — крупно, текущий подсвечен акцентом; в углу всех слайдов блока — уменьшенная версия.
- **Маркеры в углу:**
  - слайды с примером «платежи в магазине» (блоки 1–2) — пиктограмма монеты;
  - слайды, где речь про ЛР3 или защиту, — плашка «ЛР3» акцентным контуром.
- **Иконки:** минимальный набор. Книга = источник из книги Швеца; предупреждающий треугольник = антипример / не компилируется; галочка в круге = правильно; стрелка C++ → C# = сноска; две реплики = дискуссия.
- **Логотипы, обложки книг, стоковые фото, портреты людей, сгенерированные изображения не использовать.** Где нужна книга — рамка-плейсхолдер, куда лектор вставит своё изображение или QR-код.
- Код-термины в обычном тексте (`Build()`, `IPrototype<T>`, `with`) — моноширинным.
- Нижний колонтитул: номер блока и слайда, например «3.14».

Тайминг блоков: 0 — 8 мин · 1 — 12 · 2 — 10 · 3 — 25 · 4 — 25 · 5 — 7 · 6 — 3.

### Слайд 2 — Основной референс (C + плейсхолдер справа)
- **Ключевая строка:** все паттерны курса читаем по одной книге.
- А. Швец, «Погружение в паттерны проектирования», Refactoring.Guru, 2018 · Веб-версия с примерами на C#: refactoring.guru/ru/design-patterns.
- Справа — рамка-плейсхолдер «QR-код на сайт (вставит лектор)».

### Слайд 3 — Что такое паттерн (A)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 23]:** Паттерн проектирования — это часто встречаемое решение определённой проблемы при проектировании архитектуры программ.

### Слайд 4 — Паттерн — чертёж, а не рецепт (D)
- **Ключевая строка:** паттерн не копируют в код — его подстраивают под свою программу.
- Две карточки рядом: «Алгоритм — кулинарный рецепт: чёткие шаги» · «Паттерн — инженерный чертёж: решение нарисовано, шаги — нет».
- Под карточками мелко: «аналогия А. Швеца, с. 23».

### Слайд 5 — Gang of Four (C)
- **Ключевая строка:** 23 паттерна объектно-ориентированного дизайна в одной книге.
- Эрих Гамма, Ричард Хелм, Ральф Джонсон, Джон Влиссидес · *Design Patterns: Elements of Reusable Object-Oriented Software* · По-русски: «Приёмы объектно-ориентированного проектирования. Паттерны проектирования».

### Слайд 6 — Зачем знать паттерны (C)
- **Ключевая строка:** нашли паттерн в коде — быстро получили больше информации о коде.
- «Стандартные решения проще поддерживать: понятнее чужой код» · «Паттерн виден по неймингу: `PaymentFactory`, `EmailBuilder`» · «Знание применимости ускоряет поиск решения».

### Слайд 7 — Три категории (A, три плашки в ряд + строка снизу)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 25]:** Порождающие паттерны беспокоятся о гибком создании объектов без внесения в программу лишних зависимостей.
- **[ОПРЕДЕЛЕНИЕ · книга, с. 25]:** Структурные паттерны показывают различные способы построения связей между объектами.
- **[ОПРЕДЕЛЕНИЕ · книга, с. 25]:** Поведенческие паттерны заботятся об эффективной коммуникации между объектами.
- Строка под плашками (плашка «ЛР3» в углу): «Порождающие — сегодня и ЛР3 · структурные — ЛР2 · поведенческие — ЛР4».

### Слайд 8 — Порождающие паттерны (A)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 67]:** Эти паттерны отвечают за удобное и безопасное создание новых объектов или даже целых семейств объектов.
- Подзаголовок: «Формулировкой курса: отделяют абстракцией логику создания объектов от логики, эти объекты использующей».

### Слайд 9 — Пять паттернов — пять ситуаций (D)
- **Ключевая строка:** каждый паттерн отвечает на свою ситуацию создания объекта.
- Пять карточек в ряд (это и есть сквозной индикатор): «Фабричный метод / Фабрика — создаваемый тип меняется» · «Строитель — аргументов много или они собираются по шагам» · «Прототип — нужна копия» · «Одиночка — нужен ровно один объект».

### Слайд 10 — Создание — место, где проверяется инвариант (C)
- **Ключевая строка:** порождающие паттерны — способы не потерять гарантию корректности, когда создание усложняется.
- «Лекция 1: конструктор приводит объект в безопасное состояние» · «Лекция 3: паттерн — готовый ответ на „кто за что отвечает“» · «Каждый паттерн проверяем: какую ответственность отделяет, не нарушает ли SOLID».

## Блок 1. Фабричный метод (слайды 11–24)

### Слайд 11 — Разделитель «1 · Фабричный метод»
- Индикатор: подсвечен «Фабричный метод». Подзаголовок: «и почему курс считает его почти антипаттерном».

### Слайд 12 — Фабричный метод (A)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 69]:** Фабричный метод — это порождающий паттерн проектирования, который определяет общий интерфейс для создания объектов в суперклассе, позволяя подклассам изменять тип создаваемых объектов.
- Подзаголовок: «Также известен как „Виртуальный конструктор“».

### Слайд 13 — Когда применим (C)
- **Ключевая строка:** сценарий одинаковый — различаются только типы создаваемых в нём объектов.
- «Вместо дублирования сценария» · «Создание выносится в абстрактный метод» · «Его реализуют наследники». Мелко: «формулировка курса».

### Слайд 14 — Структура (D)
- **Ключевая строка:** две иерархии — создатели и продукты.
- UML-подобная схема: слева иерархия «Создатель» (абстрактный, метод `createProduct(): Продукт` курсивом) → два «Конкретных создателя»; справа иерархия «Продукт» (интерфейс) → два «Конкретных продукта»; пунктирные стрелки «создаёт» от каждого конкретного создателя к своему продукту.

### Слайд 15 — Роли (A, три плашки одна под другой)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 74]:** Продукт определяет общий интерфейс объектов, которые может произвести создатель и его подклассы.
- **[ОПРЕДЕЛЕНИЕ · книга, с. 74]:** Создатель объявляет фабричный метод, создающий объекты через общий интерфейс продуктов.
- **[ОПРЕДЕЛЕНИЕ · книга, с. 74]:** Конкретные создатели по-своему реализуют фабричный метод, производя те или иные конкретные продукты.

### Слайд 16 — Создание — не главная функция создателя (C)
- **Ключевая строка:** обычно создатель содержит и другой код работы с продуктом (по книге, с. 74).
- «Запомните эту фразу» · «На ней держится критика паттерна дальше».

### Слайд 17 — Задача: платежи в магазине (D, пиктограмма монеты)
- **Ключевая строка:** логика расчёта не изменилась, но банковскому платежу нужен счёт получателя.
- Схема в два шага: «Было: расчёт → платёж наличными» → «Стало: расчёт → платёж наличными | банковский платёж (+ счёт получателя)».

### Слайд 18 — Продукты (B, пиктограмма монеты)
- **Ключевая строка:** общий интерфейс продукта и две реализации.
- Код:
```csharp
public interface IPayment
{
    decimal Amount { get; }
}

public record CashPayment(decimal Amount) : IPayment;

public record BankPayment(decimal Amount, string ReceiverAccount) : IPayment;
```
- Сноска: `record CashPayment(decimal Amount) : IPayment` — позиционный `record` реализует интерфейс своим свойством `Amount`.

### Слайд 19 — Создатели (B, пиктограмма монеты)
- **Ключевая строка:** `Calculate` не знает, откуда берутся недостающие данные.
- Код (подсветить акцентным строку `protected abstract IPayment CreatePayment(decimal amount);`):
```csharp
public abstract class PaymentCalculator
{
    public IPayment Calculate(Order order)
    {
        return CreatePayment(order.TotalCost);
    }

    protected abstract IPayment CreatePayment(decimal amount);
}

public class CashPaymentCalculator : PaymentCalculator
{
    protected override IPayment CreatePayment(decimal amount)
        => new CashPayment(amount);
}

public class BankPaymentCalculator : PaymentCalculator
{
    private readonly string _receiverAccount;

    public BankPaymentCalculator(string receiverAccount)
    {
        _receiverAccount = receiverAccount;
    }

    protected override IPayment CreatePayment(decimal amount)
        => new BankPayment(amount, _receiverAccount);
}
```
- Справа: «Счёт получателя — в конструктор наследника» · «`order.TotalCost` — Information Expert, лекция 3».
- Сноска: `protected abstract` — чисто виртуальный метод, видимый только наследникам.

### Слайд 20 — Что пишет книга (A + список плюсов слева)
- **Ключевая строка:** у книги четыре плюса и один минус.
- Слева мелко, с галочками: «избавляет от привязки к конкретным продуктам · код производства в одном месте · проще добавлять продукты · реализует OCP» (с. 82).
- **[ОПРЕДЕЛЕНИЕ · книга, с. 83]:** Может привести к созданию больших параллельных иерархий классов, так как для каждого класса продукта надо создать свой подкласс создателя.

### Слайд 21 — Акция «Всё по N рублей» (D, пиктограмма монеты)
- **Ключевая строка:** каждый новый способ расчёта × каждый вид платежа = новый класс.
- Схема-дерево: `PaymentCalculator` → `CashPaymentCalculator`, `BankPaymentCalculator`; рядом новая ветка предупреждающим цветом: `FixedPriceCashCalculator`, `FixedPriceBankCalculator`. Между ветками перечёркнутая стрелка «переиспользовать создание платежа» с подписью «наследоваться от двух классов в C# нельзя».

### Слайд 22 — Неявное нарушение SRP (C)
- **Ключевая строка:** код разнесён по файлам, но объект-наследник отвечает за два шага сразу.
- «Шаг 1 — операция расчёта» · «Шаг 2 — выбор создаваемого типа» · «Проблемы с переиспользованием создания — признак, что SRP нарушен».

### Слайд 23 — Книга и курс расходятся в оценке (F)
- **Ключевая строка:** книга показывает паттерн; решение о применимости — ваше.
- Колонка «Книга Швеца» (с. 83): «Нормальный паттерн с одним минусом — параллельные иерархии» · «Многие архитектуры начинаются с него и эволюционируют к фабрике, прототипу или строителю».
- Колонка «Курс»: «Минус из книги — следствие наследования, не мелочь» · «Плюс неявное нарушение SRP» · «Почти антипаттерн. Don't 11; принцип из той же книги — „Предпочитайте композицию наследованию“, с. 44».
- Правило для ЛР3: «Фабричный метод без обоснования — вопрос „почему не фабрика?“ „Так в книге“ — не обоснование».

### Слайд 24 — Дискуссия (E, плашка «ЛР3»)
- Вопрос: «Как добавить акцию „Всё по N рублей“, не создавая новую иерархию калькуляторов?»
- Подсказка: «Калькулятор *является* создателем платежей — или *содержит* его?»

## Блок 2. Фабрика: композиция вместо наследования (слайды 25–36)

### Слайд 25 — Разделитель «2 · Фабрика»
- Индикатор: подсвечена «Фабрика». Подзаголовок: «композиция вместо наследования».

### Слайд 26 — «Является» и «содержит» (A)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 45]:** Если наследование можно выразить словом «является» (автомобиль является транспортом), то композицию — словом «содержит» (автомобиль содержит двигатель).
- Подзаголовок: «Калькулятор не является создателем платежей — он содержит фабрику платежей».

### Слайд 27 — Абстрактная фабрика (A)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 85]:** Абстрактная фабрика — это порождающий паттерн проектирования, который позволяет создавать семейства связанных объектов, не привязываясь к конкретным классам создаваемых объектов.

### Слайд 28 — Методы абстрактной фабрики (A)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 91]:** Абстрактная фабрика объявляет методы создания различных абстрактных продуктов.

### Слайд 29 — Ключевое слово — семейство (D)
- **Ключевая строка:** продукты одной фабрики гарантированно сочетаются.
- Таблица 3 × 3 (пример книги): столбцы «Кресло · Диван · Столик», строки «Ар-деко · Викторианский · Модерн». Строка «Модерн» выделена акцентом с подписью «фабрика „Модерн“ создаёт только эту строку».

### Слайд 30 — Фабрика на курсе (C, пиктограмма монеты)

```csharp
    public Prototype(IReadOnlyCollection<int> relatedEntityIds)
    {
        _relatedEntityIds = relatedEntityIds;
    }

    public Prototype Clone()
    {
        return new Prototype(_relatedEntityIds);
    }
}
```

### Слайд 74 — Единственный минус прототипа по книге (A)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 130]:** Сложно клонировать составные объекты, имеющие ссылки на другие объекты.
- Подзаголовок: «Как именно сложно — в книге не разобрано. Дальше — формулировки курса».

### Слайд 75 — Поверхностная копия (A + мини-схема)
- **[ОПРЕДЕЛЕНИЕ · курс]:** “shallow copy” (поверхностная копия). Так мы называем копирование, подразумевающее сохранение ссылок на объекты, содержащиеся в объекте-прототипе.
- Мини-схема под плашкой: «оригинал» и «копия» — две рамки, обе стрелками указывают на одну и ту же «коллекцию».

### Слайд 76 — Глубокая копия (A + мини-схема)
- **[ОПРЕДЕЛЕНИЕ · курс]:** “deep copy” (глубокая копия). В таком случае, мы создаём копии всех объектов, достижимых из объекта-прототипа, при его копировании.
- Мини-схема: «оригинал» → «коллекция», «копия» → «копия коллекции».

### Слайд 77 — Глубокая копия в коде (B)
- **Ключевая строка:** каждый элемент коллекции клонируется сам.
- Код (подсветить акцентным `_values.Select(x => x.Clone()).ToList()`):
```csharp
public class WrappedValue
{
    public int Value { get; set; }

    public WrappedValue Clone()
    {
        return new WrappedValue { Value = Value };
    }
}

public class DeepCopyPrototype
{
    private readonly List<WrappedValue> _values;

    public DeepCopyPrototype(List<WrappedValue> values)
    {
        _values = values;
    }

    public DeepCopyPrototype Clone()
    {
        List<WrappedValue> values = _values.Select(x => x.Clone()).ToList();
        return new DeepCopyPrototype(values);
    }
}
```
- Справа: «`set` здесь намеренно — иначе глубокая копия не нужна» · «В ЛР так не пишем: Do 10, Don't 20».

### Слайд 101 — Одиночка (A)
- **[ОПРЕДЕЛЕНИЕ · книга, с. 133]:** Одиночка — это порождающий паттерн проектирования, который гарантирует, что у класса есть только один экземпляр, и предоставляет к нему глобальную точку доступа.

- Подзаголовок: «Единственный экземпляр + глобальная точка доступа».

### Слайд 103 — Double checked lock (B)
- **Ключевая строка:** вторая проверка — не создал ли объект другой поток, пока текущий ждал на `lock`.
- Код (подсветить акцентным обе строки `if (_instance is not null)`):
```csharp
public class Singleton
{
    private static readonly object _lock = new();
    private static Singleton? _instance;

    private Singleton() { }

    public static Singleton Instance
    {
        get 
        {
            if (_instance is not null)
                return _instance;

            lock (_lock)
            {
                if (_instance is not null)
                        return _instance;

                return _instance = new Singleton();
            }
        }
    }
}
```
- Сноска: `lock (_lock) { … }` — как `std::lock_guard` на мьютексе; в .NET 9+ есть отдельный тип `System.Threading.Lock`.

### Слайд 104 — Режимы `Lazy<T>` (D, таблица 3 строки)
- **Ключевая строка:** полную потокобезопасность даёт только `ExecutionAndPublication`.

| Режим | Сколько раз вызовется фабрика | Какое значение останется |
|---|---|---|
| `None` | может несколько | одного из потоков — неопределённо |
| `PublicationOnly` | может несколько | созданное первым зашедшим потоком |
| `ExecutionAndPublication` | ровно один | единственное |

- Строку `ExecutionAndPublication` — акцентным фоном.

### Слайд 105 — Одиночка через `Lazy<T>` (B)
- **Ключевая строка:** потокобезопасность — забота `Lazy<T>`, не ваша.
- Код:
```csharp
public class Singleton
{
      private static readonly Lazy<Singleton> _instance;

      static Singleton()
      {
          _instance = new Lazy<Singleton>(() => new Singleton(), LazyThreadSafetyMode.ExecutionAndPublication);
      }

      private Singleton() { }

      public static Singleton Instance => _instance.Value;
}
```
- Сноска: `static Singleton()` — статический конструктор: один раз, потокобезопасно, при первом обращении к типу — как `static`-переменная в функции в C++11.
